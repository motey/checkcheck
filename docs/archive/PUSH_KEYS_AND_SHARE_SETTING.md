# Plan: push keys without configuration, and one share setting instead of two

**Status:** done (written 2026-08-04, both chunks landed 2026-08-05).

Two maintainer decisions taken after the notification branch was reviewed:

1. **Push should work without an operator generating anything.** Today
   `NOTIFY_PUSH_ENABLED` defaults to false and turning it on without
   `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_CONTACT_EMAIL` refuses to
   boot, so push is off on every instance nobody hand-configured. The fix is to
   generate the key pair on first boot and persist it.
2. **"A card is shared with me" and "I am invited to a card" are one thing to a
   user.** They are the two halves of one event, selected by
   `SHARING_REQUIRE_INVITE_ACCEPT`, so on any instance only one of them can ever
   fire and the other row in the settings dialog is dead. One row, controlling
   both.

Both are scheduled for the next release.

---

## 0. Standing rules

- Every behaviour change gets a backend test, run on **both**
  `./run_backend_tests_with_sqlite.sh` and `./run_backend_tests_with_postgres.sh`.
- Anything a user clicks gets vitest and/or Playwright coverage.
- No em dashes or en dashes anywhere.
- Schema changes are real autogenerated Alembic revisions on top of the current
  head (`0016_push_subscription`). P1 needs one; P2 does not.
- New settings go into `config.py` with a `title` and `description`, then
  `./gen_config_docs.sh`.
- **The maintainer commits, nobody else.**

## 1. Decisions settled before chunking

| # | Question | Decision |
|---|---|---|
| 1 | Gate generation on `SERVER_PUBLIC_URL` being https? | **No, and it would be backwards.** A VAPID pair is a P-256 keypair; it has no relationship to the URL, the certificate or TLS, and generating one costs about a millisecond. The secure-context requirement is the *browser's*, on the page doing `PushManager.subscribe`, and `http://localhost` and `http://127.0.0.1` **are** secure contexts. So an https gate would disable push on the one no-TLS case that works (a localhost dev instance) while doing nothing for the case that is actually broken (plain http on a LAN IP or a hostname), where the browser refuses whatever the server does. Generate unconditionally. |
| 2 | Where do the keys live? | **A new `instance_secret` table**, one row per named secret. Not a file: the container filesystem may be read-only or ephemeral, and two replicas writing their own file would each sign with a different key, which is a broken instance that looks fine. The database is the one thing every replica already shares and the deployment already persists. |
| 3 | What happens to explicitly configured keys? | **They win, and nothing is generated.** `VAPID_PUBLIC_KEY` and friends stay in `config.py` and keep their boot validation exactly as it is: a half-configured pair is still a startup error, because an operator who set one of the three meant to set all three. Generation is only for the case where none of them is set. |
| 4 | Does `NOTIFY_PUSH_ENABLED` default to true? | **Yes, once generation exists**, which is the whole point: with a key pair guaranteed, the flag no longer has a way to fail. It stays a real switch for an operator who wants push off. |
| 5 | What about the "browser does not support push" hint? | **Reword it to name the real reason.** On a page that is not a secure context the current wording blames the browser for the deployment's missing TLS. `window.isSecureContext` is the exact check, and the fix is frontend-only. Falls out of decision 1: this is the case an https gate would have been trying to serve, handled where the user can actually read it. |
| 6 | One row for the two share types: where? | **In the frontend, writing both types.** The API already accepts a multi-type patch in one `PUT`, so the merged control sends `{card_shared: {...}, card_invited: {...}}` and the two can never drift. No endpoint change, no response change, and an operator who flips `SHARING_REQUIRE_INVITE_ACCEPT` finds the user's choice already applies to the type that is now live. |
| 7 | What does the merged row show? | **The live type's cell**, chosen from `SHARING_REQUIRE_INVITE_ACCEPT` if the client can see it, else `card_shared`. A lock on **either** type locks the row, so an administrator's cap can never be hidden by the merge. |

## 3. K1: VAPID keys on first boot

**Goal:** a fresh instance sends push notifications without anybody running
`gen_vapid_keys.sh`.

**Changes:**

- **`model/instance_secret.py`**, a new table: `name` (primary key, short string),
  `value` (text), plus the usual timestamps. General on purpose, since this is not
  the last instance-level secret this app will want, but **do not** build a config
  system on it: it holds generated secrets, not operator settings.
- **Alembic revision `0017`**, on top of `0016`, in the style the other four use
  (guarded DDL so it is a no-op when `create_all` got there first, and re-runnable).
- **`notify/vapid.py`**, the resolution layer and the only thing that answers "what
  key does this instance sign with":
  - configured keys win (decision 3),
  - otherwise read `vapid_public_key` / `vapid_private_key` from `instance_secret`,
  - otherwise generate a pair (`py_vapid`'s `Vapid02`, the same library the boot
    check already loads), insert it, and return it,
  - the insert is racy across replicas: use the primary key conflict, and on a
    lost race re-read the winner's row rather than overwriting it. `db/push_subscription.upsert`
    is the pattern already in the codebase.
- **Populate it once, at startup, not per request.** The dispatcher's lifespan in
  `notify/dispatcher.py` is the obvious home. The resolved pair goes in a
  module-level holder that the two read sites use:
  `notify/push.py:226` (the private key, at send time) and
  `api/routes/routes_public_config.py:116` (the public key, for the browser).
  Both read `config.VAPID_*` today and must stop.
- **`config.py`**: `NOTIFY_PUSH_ENABLED` defaults to true (decision 4). The three
  `VAPID_*` settings stay exactly as they are, including the pair-correspondence
  check, but the "enabled but not set" error goes away: not set now means
  generated. Update the descriptions to say so, then `./gen_config_docs.sh`.

**Traps, in the order they will bite:**

- **`Config` cannot do this.** The boot validator runs inside `Config`'s own model
  validation, has no database and no event loop, and `notify/push.py` is imported
  from inside it (which is why that module may not import `checkcheckserver.log`).
  Generation belongs in the lifespan, after the engine exists. Do not try to make
  `Config.VAPID_PUBLIC_KEY` resolve to a generated value.
- **`routes_public_config.py` has no session today** for this. Check before
  assuming it can read the table per request; the module-level holder above is
  what avoids needing one.
- **Losing the row unsubscribes every device.** A restored-from-scratch database
  gets a new pair, every existing `push_subscription` then fails with a 403, and
  under chunk N3 those rows fail permanently rather than deleting the device.
  Document it in `docs/UPGRADING.md` next to the backup guidance, and consider
  whether a 403 should eventually mean "resubscribe" client-side (it should not
  mean "delete", which N3 established deliberately).
- **The dev scripts and the E2E harness pin their own pair** and must keep
  working unchanged: that is decision 3 doing its job, and it is the cheapest
  regression test that configured keys still win.

**Tests:**

- A fresh database generates a pair, and the pair passes `validate_vapid_keys`.
- A second boot reuses it (same public key, one row).
- Configured keys win: nothing is generated and no row is written.
- Two concurrent resolutions produce one row and one key.
- `GET /api/public-config` serves the generated public key.

**Done when:** both backend suites are green, a fresh instance with no push
configuration at all can subscribe a browser, and `./gen_config_docs.sh` has been
run.

## 4. K2: one share setting, and the secure-context hint

**Goal:** the settings dialog stops showing a row that cannot fire, and stops
blaming the browser for a missing certificate.

**Changes:**

- **`utils/notificationSettings.ts`**: `typeRows()` renders `card_shared` and
  `card_invited` as one row. Wording for the merged row goes in `TYPE_WORDING`
  ("A card is shared with me", described so it covers both policies without
  naming either). The cell comes from the live type (decision 7), and the lock is
  the OR of the two.
- **`prefsPatch()`** returns both types for that row, which is what keeps them in
  lockstep. It already returns the right shape for a multi-type patch, so this is
  an argument change, not a new function.
- **The E2E specs address cells by `notification-mode-{type}-{channel}`**, and
  `card_invited`'s cells disappear. Expect to touch
  `tests/e2e/notification-settings.spec.ts`; keep `card_shared` as the testid of
  the merged row so most of it survives.
- **The push hint** in `NotificationSettingsModal.vue`: when
  `window.isSecureContext` is false, say that push needs https (and that
  localhost is fine for development) instead of "This browser does not support
  push notifications". Keep the existing wording for a browser that really lacks
  the APIs; they are two different problems and only one of them is the user's.

**Tests:** vitest for the merged row (one row, both types in the patch, a lock on
either type locks it) and for the hint selection; the E2E updates above.

**Done when:** the dialog has one share row on both share policies, the vitest
and Playwright suites are green.

### K1, as built

Everything the plan called for, plus four things worth writing down:

- **The JWT `sub` claim needed a fallback of its own.** `VAPID_CONTACT_EMAIL` was
  required alongside the keys, so dropping the "enabled but not set" error meant
  deciding what an instance with no contact address signs with. RFC 8292 accepts a
  `mailto:` or an `https:` URI, so `notify/vapid.resolve_subject` falls back to
  `ADMIN_USER_EMAIL` and then to `SERVER_PUBLIC_URL`: both are true about the
  instance rather than invented for the claim.
- **The half-configured check changed shape.** Setting neither half is now the
  normal case and setting both is still validated exactly as before, so what is
  left to reject is setting *one* of them, which is what `Config._validate_push`
  now does. `VAPID_CONTACT_EMAIL` is no longer part of that check.
- **`keys_for(config)` exists for the synchronous send site.** `notify/push.py`
  reads the module holder, but cannot await and must still work in a process that
  never ran the lifespan (a test driving `_send_sync`, or an out-of-process
  drain). It falls back to the *configured* pair only, never to a generated one:
  generating needs a database and a decision about who wins the race, and
  guessing either from a send site is how two replicas end up signing with
  different keys. With no key at all the send raises `PushEndpointRefused`, so
  the row fails and no device is unsubscribed (chunk N3's classification).
- **The backend test harness flipped with the default.** The live test server now
  boots the way an unconfigured instance does: push on, no `VAPID_*`, so it
  generates a pair and `tests_vapid_keys.py` asserts the whole path end to end
  (including `GET /api/public-config` serving the public half of the key the
  server actually stored). The four disabled-instance checks that used to run
  against it moved in-process behind a `push_disabled_routes` fixture, and two
  "no channel is enabled" assertions in `tests_notification_outbox.py` /
  `tests_reminder_scan.py` had to say `NOTIFY_PUSH_ENABLED=False` out loud: an
  instance with push on genuinely has a channel.

**One trap the plan did not predict.** Adding the resolution to the dispatcher's
lifespan gave `test_lifespan_starts_the_dispatcher_and_stops_it_again` a database
query it never had. That test drives its own `asyncio.run` without disposing the
engine, so on Postgres it left an asyncpg connection in the pool bound to a dead
loop and the *next* test in the file failed with "attached to a different loop".
The resolution is stubbed out there (the test is about the task), and
`tests_vapid_keys.py` asserts the lifespan really does fill the holder, including
on an instance with `NOTIFY_DISPATCH_IN_PROCESS=false` where the loop stays down
but `/api/public-config` still has to answer.

### K2, as built

- **`typeRows` takes the share policy as a third argument** and collapses the two
  share types into one row keyed `card_shared`, so every existing testid and
  saved-cell key survived. `TypeRow` gained a `types: string[]`, which is what
  `prefsPatch` now takes, and `onModeChange` takes the row rather than a type
  string.
- **The lock is the OR of the two halves, and so is the mode it displays.** A cap
  on the dormant type would otherwise be invisible until an operator flipped the
  flag, with the control offering a mode the server was never going to honour.
- **The three hints became one selector.** `pushUnavailableReason` in
  `utils/push.ts` orders insecure-context before iOS-install before unsupported,
  because a browser on an insecure page also tends to hide the push APIs and the
  useful sentence is the one naming the cause. The template still renders three
  separate elements so each keeps its own testid.
- **The insecure-context case cannot be reached by the E2E harness** (`localhost`
  is a secure context by definition, which is exactly why the wrong wording
  survived so long), so its Playwright test stubs `window.isSecureContext`.
