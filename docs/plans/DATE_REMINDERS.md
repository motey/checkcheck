This document is the full implementation brief for a multi-session sub-project,

## 0. Standing rules for every session in this sub-project

Identical to section 0 of `EMAIL_NOTIFICATIONS.md`, which is the authority. In
short, and non-negotiable:

- **Working code, not a prototype.** Every new behaviour gets a backend test in
  `CheckCheck/backend/tests/`, and both `./run_backend_tests_with_sqlite.sh` and
  `./run_backend_tests_with_postgres.sh` pass before a chunk is called done.
  Frontend logic gets vitest specs, anything a user clicks gets Playwright.
  Never leave a `TODO` in place of a test.
- **Test the failure paths.** For reminders those are the interesting ones: the
  card was tombstoned, access was revoked, the user's time zone is unusable, the
  monthly date does not exist in the target month, the clock jumped over a DST
  boundary, the server was down when the reminder came due.
- **Every session ends with a cold-start prompt** overwritten into
  `NEXT_SESSION.md` (not committed), and with the progress table in section 10 of
  *this* document updated honestly.
- **No em dashes or en dashes** anywhere: docs, comments, commit messages, UI copy.
- **Schema changes ship as real autogenerated Alembic revisions** on top of the
  current head, `0014_user_notification_settings`. Model definitions must be
  correct on their own for a fresh Postgres database (naive UTC datetimes,
  `ondelete="CASCADE"` on foreign keys), because the test harness runs
  `create_all` before migrations.
- **New settings** go into `config.py` with a `title` and `description`, then
  `./gen_config_docs.sh`. Endpoint or response-model changes mean regenerating
  `CheckCheck/openapi.json` and then `bun run postinstall` in the frontend.
- **Trap:** `CheckCheck/openapi.json` carries a build-metadata `version` line that
  every backend and E2E run rewrites, and `source build_server_dev_env.sh`
  re-resolves `CheckCheck/backend/pdm.lock`. Revert both before committing.
- **Trap:** never run two backend test invocations at once (shared port 8888 and
  SQLite file), same for two E2E runs (port 8182).

## 1. Orientation: what already exists

The email sub-project left this feature about two thirds built. What is already
there, and what each piece gives us:

| Piece | Where | What it does for reminders |
|---|---|---|
| `emit_notification` | [`db/notification.py`](../../CheckCheck/backend/checkcheckserver/db/notification.py) | The single emission seam. It already fans one event out to in-app, email and webhook according to the user's preferences. A reminder is just a fourth notification type through it. |
| `dispatcher_loop` | [`notify/dispatcher.py`](../../CheckCheck/backend/checkcheckserver/notify/dispatcher.py) | A lifespan-started loop with per-tick work (`dispatch_once`) already separated from hourly housekeeping (`_prune`). The due-reminder scan is a per-tick addition beside `dispatch_once`. |
| `notification_outbox` | [`notify/outbox.py`](../../CheckCheck/backend/checkcheckserver/notify/outbox.py) | Retries, coalescing, dead-lettering. Reminders inherit all of it for free by going through `emit_notification`. |
| Per-user `timezone` | [`model/user_notification_settings.py:73`](../../CheckCheck/backend/checkcheckserver/model/user_notification_settings.py) | Added in E3 **specifically so this feature needs no migration for it**. Already validated as an IANA name and already used by the daily digest. |
| `notify/schedule.py` | [`notify/schedule.py`](../../CheckCheck/backend/checkcheckserver/notify/schedule.py) | `_zone()` already does the "stored zone stopped being valid, fall back to UTC and warn" dance. Reuse it, do not write a second one. |
| `_add_user_has_access_query` | [`db/checklist.py:60`](../../CheckCheck/backend/checkcheckserver/db/checklist.py) | The one predicate that means "this user can see this card": owner or accepted collaborator, tombstone masked, position row required. It is exactly the fire-time check this feature needs, and using it means every future way of losing access is covered without touching this code. |
| The deep link | `notify/render.py` | Mail already links `/?card=<id>&n=<notification_id>`, and the SPA already translates it and marks the notification read on open. A reminder mail gets that for nothing. |

Facts that shape the design:

- **Checklists are never hard-deleted.** `SoftDeleteMixin` tombstones them
  (`deleted_at`) and tombstone GC is explicitly deferred to 2.1+. So a foreign
  key with `ondelete="CASCADE"` is correct but will essentially never fire, and
  the tombstone check at fire time is the mechanism that actually matters.
- **The dispatcher tick defaults to 30 seconds** (`NOTIFY_DISPATCH_TICK_SECONDS`),
  so a reminder fires within one tick of its time. That is the precision this
  feature offers, and it is fine: nobody sets a checklist reminder to the second.
- **The server runs a single uvicorn process.** The scan claims rows with the
  same conditional `UPDATE ... WHERE status = 'pending'` the outbox uses, which
  is what actually prevents a double fire and leaves no row stuck if the process
  dies mid-scan.
- **Notification settings are an online-only surface** (WI-12 pattern:
  `assertOnline` plus `useConnectivity`, never queued in the offline outbox).
  Reminders follow the same rule, see decision 6.

## 2. Decisions settled with the maintainer

These three were the open questions `EMAIL_NOTIFICATIONS.md` section 8 left, plus
what fell out of answering them. Do not re-open without a concrete trigger.

1. **A reminder belongs to the user who set it, and only they are notified.**
   A reminder is personal, not a property of the card. Any collaborator can set
   their own on the same card, and nobody can make somebody else's phone buzz.
   The row therefore carries exactly one `user_id`, the fan-out is a single
   `emit_notification` call, and there is no permission question about who may
   schedule mail for whom. This is also what the plan's own wording asked for:
   "notify me about that checklist at date".

2. **Validity is re-checked when the reminder fires, and a reminder that cannot
   be delivered is cancelled silently.** The row survives a deletion or a
   revocation; just before emitting, the scan asks
   `_add_user_has_access_query` whether this user can still see this card, and
   marks the row `cancelled` if not. One authoritative check, immune to every
   path that can take access away (direct share removal, group share
   reconciliation, self-leave, tombstone), and it costs nothing until the row is
   due. The alternative, cancelling eagerly at each revocation seam, was
   rejected: it is four or five call sites that must all stay correct forever,
   and any one of them missed leaks a notification about a card the recipient
   can no longer open. Silently, because a "your reminder was cancelled" message
   about a card somebody just deleted is noise about a thing they did on purpose.

3. **The first cut is card-level, one-off plus simple recurrence** (`daily`,
   `weekly`, `monthly`). Item-level reminders are out (section 8).

4. **Recurrence rolls forward in the reminder's own time zone, not in UTC.**
   "Every day at 09:00" means the wall clock, so the next occurrence is computed
   by converting to local time, adding the interval there, and converting back.
   Adding 24 hours in UTC would walk the reminder an hour off every DST change.

5. **The reminder carries its own `timezone` column**, snapshotted from the
   user's notification settings at creation (falling back to the zone the client
   sends, then UTC). The per-user zone in E3 is what *populates* it, not what is
   read at roll-forward time. Reason: a user who moves and changes their global
   zone should not silently find every existing recurring reminder shifted, and a
   reminder created before the user ever opened the settings dialog still needs a
   zone. One column, and the ambiguity disappears.

6. **Reminders are an online-only surface.** They are per-user data attached to a
   card but not part of the card entity, so they stay out of the delta feed and
   out of the offline outbox, exactly like notification settings. Setting a
   reminder while offline is refused with the existing `assertOnline` notice
   rather than queued. Reason: a queued reminder whose fire time passes before
   the queue drains is worse than useless, and the sync contract has no shape for
   per-user side data.

7. **`reminder_due` ships with `email: immediate` in the instance defaults**,
   which is a deliberate exception to the E3 rule that a new notification type
   never starts mailing on its own. That rule protects users from a release
   quietly signing them up for mail about something they did not ask for. A
   reminder is the opposite: the user explicitly asked to be told at a time when
   they will not be looking at the app, so in-app only would make the feature
   pointless.

8. **`reminder_due` accepts only `off` and `immediate` on the email channel.**
   A reminder in tomorrow morning's digest is not a reminder. This needs a
   per-type mode restriction in `prefs.py`, which today only has per-channel
   ones, so it is real work rather than a config default. See R3.

## 3. Data model

### 3.1 `scheduled_notification` (new table, chunk R1)

Alembic revision `0015`, on top of `0014_user_notification_settings`.

```python
class ScheduledNotification(TimestampedModel, table=True):
    __tablename__ = "scheduled_notification"

    id: uuid.UUID                       # pk
    user_id: uuid.UUID                  # FK user, CASCADE, indexed. The setter,
                                        # and the only recipient (decision 1).
    cl_id: uuid.UUID                    # FK checklist, CASCADE, indexed.
    remind_at: datetime.datetime        # naive UTC, indexed. The next (or only)
                                        # time this fires.
    timezone: Optional[str]             # IANA name, decision 5. Null means UTC.
    recurrence: ReminderRecurrence      # enum-as-string, default `none`.
    note: Optional[str]                 # max 200 chars, the user's own text.
    status: ReminderStatus              # enum-as-string, default `pending`.
    last_fired_at: Optional[datetime]   # naive UTC, null until it first fires.
    fire_count: int                     # default 0, bumped on each fire.
```

- `ReminderRecurrence`: `none`, `daily`, `weekly`, `monthly`.
- `ReminderStatus`: `pending`, `done` (a one-off that fired), `cancelled` (the
  fire-time check failed, or the user removed it).
- Both are `str, enum.Enum` stored via `sa_type=String`, matching
  `NotificationType`, `SharePermission` and `ShareStatus`.
- The composite index that matters is `(status, remind_at)`: the scan's only
  query is "pending rows due now", and it runs every tick forever.
- Like the outbox and the settings table, this is **not** a syncable entity: no
  client sees it through the delta feed, and it gets no `SoftDeleteMixin`. A
  removed reminder is a real `DELETE` or a `cancelled` row, not a tombstone.
- **Caps, as module constants rather than settings** (following the
  `schedule.DAILY_DIGEST_HOUR` precedent): `MAX_PENDING_PER_CARD = 10` and
  `MAX_PENDING_PER_USER = 200`. Enforced on create with a 409. If an operator
  ever needs to tune these they become settings then, not now.
- **Retention**, also a module constant: `done` and `cancelled` rows older than
  `REMINDER_RETENTION_DAYS = 30` are removed in the dispatcher's existing hourly
  housekeeping pass, next to `prune_once` and `prune_feed_once`. The notification
  the reminder produced is the durable record; the schedule row is not.

### 3.2 `reminder_due` (new `NotificationType` member)

```python
reminder_due = "reminder_due"  # a reminder the user set on a card came due
```

Payload keys: `checklist_name` and `note` (the user's own text), both subject to
`NOTIFY_EMAIL_CONTENT_MODE: minimal` stripping in the renderer exactly as card
titles and actor names already are. There is no actor: the user is reminding
themselves, so the payload carries no `actor_display_name` and the immediate
dedupe key falls into its existing "no actor" branch, which is right (several
reminders coming due together are one mail).

## 4. The recurrence rules

These are the whole of chunk R1's interesting logic, and they are pure functions
in a new `notify/recurrence.py` with no database access, so they are cheap to
test exhaustively.

`next_occurrence(after, *, recurrence, timezone_name) -> Optional[datetime]`,
naive UTC in and naive UTC out:

- `none` returns `None`. The caller marks the row `done`.
- `daily` / `weekly` add 1 day / 7 days **in local time**, so the wall-clock time
  is preserved across a DST change.
- `monthly` adds one calendar month in local time and **clamps to the last day of
  the target month**: a reminder on the 31st fires on 28 or 29 February, and then
  on 31 March again, because the clamp applies to the computed occurrence and
  never rewrites the stored day. That requires keeping the original day of month
  somewhere, and R1 settled it as a real column (`anchor_day`, set at creation
  from the first occurrence in the row's own zone). Deriving it from `fire_count`
  was the alternative and it is wrong: it only reconstructs the original day if
  every intervening occurrence stepped uniformly, which is exactly what a clamp
  breaks.
- **A local time that does not exist** (the hour a spring-forward skips) or that
  exists twice (autumn) is resolved by `zoneinfo`'s default `fold=0` behaviour,
  which picks the first of a repeated hour and shifts a skipped one forward. This
  is a documented choice, not an accident, and it gets a test.
- **A missed occurrence never fires late in bulk.** If the server was down for
  three days, a daily reminder does not deliver three notifications: the roll
  forward loops until the next occurrence is in the future, firing **once**.
  Anything else means a restart after a long outage floods somebody's inbox.

## 5. The scan

New module `notify/reminders.py`, one function the dispatcher calls:

```python
async def scan_due_once(session, *, config, now=None) -> ReminderScanResult
```

Per tick, bounded (`SCAN_BATCH_LIMIT = 100`, so one slow tick cannot hold the
loop):

1. Select `pending` rows with `remind_at <= now`, oldest first, limited.
2. Claim each with a conditional `UPDATE ... WHERE id = :id AND status =
   'pending'`, the same claim shape `outbox.drain_once` uses. A row whose update
   affects zero rows was taken by someone else, so skip it.
3. **Re-check validity** (decision 2): run `select(CheckList.id).where(CheckList.id
   == row.cl_id)` through `_add_user_has_access_query(query, row.user_id)`. No
   result means the card is tombstoned, or the user lost access, or the user's
   position row is gone. Mark `cancelled`, log at debug, move on.
4. `emit_notification(...)` with `type=reminder_due`. That single call does the
   in-app row, the SSE nudge, the mail and the webhook according to the user's
   preferences, and it never raises at its caller.
5. Roll forward: `next_occurrence(...)`. A datetime means set `remind_at` to it
   and leave the row `pending`; `None` means mark it `done`. Either way bump
   `fire_count` and set `last_fired_at`.

Dispatcher changes this forces, both worth calling out because they are easy to
get wrong:

- `dispatch_enabled()` currently returns true only when a channel is enabled or
  feed retention is on. **Reminders must start the loop too**, because an
  in-app-only reminder works on an instance with neither mail nor webhooks.
- `dispatch_once()` currently returns early **without opening a session** when no
  channel is enabled. It must now open one for the scan regardless, and skip only
  the drain. Keep that skip: an instance with no channels still must not poll a
  table nothing can write to.

## 7. API surface

All authenticated, all scoped to the current user, all online-only (decision 6).

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/checklist/{checklist_id}/reminders` | The caller's own reminders on this card, soonest first. Needs `view`. `?include_finished=true` also returns fired and cancelled ones. |
| `POST` | `/api/checklist/{checklist_id}/reminders` | Create. Needs `view` (you may remind yourself about a card you can only read). 400 for a time in the past or a bad zone, 409 over a cap or when the type is disabled instance-wide. |
| `PATCH` | `/api/reminder/{reminder_id}` | Change time, recurrence or note. A new time also revives a finished reminder, which is what a snooze is. 404 if the row is not the caller's, never 403: a reminder somebody else set is not a thing the caller may learn about. |
| `DELETE` | `/api/reminder/{reminder_id}` | Real delete, not a tombstone. 404 as above. |
| `GET` | `/api/user/me/reminders` | Everything upcoming, across cards, minus anything on a card the caller can no longer open. Feeds a future "my reminders" view. |

The path parameter is `checklist_id` rather than the `cl_id` this table first
said, because `require_checklist_permission` resolves the card from a parameter
of that name (see the R3 row in section 10).

Response model carries the row plus the resolved `checklist_name`, so the list
view does not need a second round trip.

## 9. Explicitly out of scope

- **Item-level reminders.** The table would need a nullable item FK, item
  tombstone handling and a second place in the UI. Card-level first; the schema
  in 3.1 can take a nullable `cli_id` later without breaking anything.
- **Reminders for other people.** Decision 1. If it is ever wanted it is a new
  audience column plus a permission rule, not a change to this shape.
- **Complex recurrence** (every second Tuesday, weekdays only, RRULE). The three
  simple rules cover what a checklist app needs. Anything beyond means adopting
  an RRULE library, which is a decision on its own.
- **Snooze.** Genuinely useful, and the natural next thing: it is a `PATCH` on
  `remind_at` from the notification itself, so the API already supports it and
  only the UI is missing. Left out to keep R4 small.
- **Per-card mute.** `EMAIL_NOTIFICATIONS.md` section 8 said this "belongs with
  the reminder feature", but that turned out to be wrong for the shape we chose:
  a reminder is self-inflicted, so muting a card does not protect anybody from
  anything. It stays a sharing-notifications feature.
- **A calendar export (iCal feed).** Frequently the real request behind "remind
  me": people want it in the calendar they already watch. It is a read-only
  signed-URL surface over this same table and it is a much better fit for a
  fourth chunk *later* than more UI now. Note it, do not build it.
