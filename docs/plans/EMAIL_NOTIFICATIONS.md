# Plan: notification transports (email, later webhooks)

**Status:** 📋 Planned, not started. Written 2026-08-01 with the maintainer.

This document is the full implementation brief for a multi-session sub-project.
It is split into **session-sized chunks (E1 to E6)**. Read section 0 (rules), the
orientation in section 1, and then only the chunk you are working on. Every chunk
is independently shippable: after each one the app must be green, migrated and
usable.

---

## 0. Standing rules for every session in this sub-project

These are non-negotiable and apply to E1 through E6.

### 0.1 We ship working code, not a prototype

The maintainer (a single human) manually tests every chunk and will find the bugs
you leave behind. Budget accordingly:

- **Backend:** every new behaviour gets a test in `CheckCheck/backend/tests/`,
  following the existing style (see `tests_sharing_notifications.py`). Run both
  `./run_backend_tests_with_sqlite.sh` and `./run_backend_tests_with_postgres.sh`
  before declaring a chunk done. Postgres is the production target; SQLite is
  local-dev only.
- **Frontend:** unit specs under `frontend/tests/unit/` (vitest) for pure logic,
  Playwright E2E under `frontend/tests/e2e/` for anything a user clicks.
- **Test the failure paths, not just the happy path.** For this feature the
  interesting cases are almost all failures: SMTP down, user has no email address,
  preference says off, throttle window still open, duplicate enqueue, dead-letter
  after N attempts, unsubscribe token expired or forged.
- **Never leave a `TODO` in place of a test.** If a chunk's tests cannot be
  written, the chunk is not done: say so in the handoff instead of claiming
  completion.
- A few DnD and sharing E2E specs fail non-deterministically. Re-run before
  blaming your change.

### 0.2 Every session ends with a cold-start prompt

The last action of every session is to **overwrite `NEXT_SESSION.md`** at the repo
root with a cold-start prompt for the following session, written as **raw
markdown** (the file is a throwaway scratch note and is not committed). It must
contain, at minimum:

- which chunk was just finished and which is next,
- what was actually built versus what this plan specified, including every
  deviation and why,
- anything left broken, skipped or deferred, stated plainly,
- the exact commands to re-run the relevant tests,
- the file paths a fresh session needs to open first.

Also update the **Progress / handoff** table at the bottom of *this* document, so
the durable record lives in git even though `NEXT_SESSION.md` does not.

### 0.3 Writing style

No em dashes or en dashes anywhere in docs, comments, commit messages or UI copy.
Use a comma, colon, parenthesis or a separate sentence.

### 0.4 Schema changes

The 2.0 schema is frozen. Every schema change ships as a real autogenerated
Alembic revision in `CheckCheck/backend/migrations/versions/`, on top of the
current head (`0012_group_shares_living_membership`). Note the create-all-before-
migrations quirk of the test harness: model definitions must be correct for a
fresh Postgres database on their own (naive UTC datetimes, `ondelete="CASCADE"`
on foreign keys).

Watch the `_base_model.py` gotcha: `Field` imported in that module is **pydantic's**
`Field`, so `index` / `primary_key` / `nullable` are ignored there. Use
`from sqlmodel import Field as SQLField` for real DB columns in that file.

### 0.5 Config changes

New settings go into `CheckCheck/backend/checkcheckserver/config.py` with a
`title` and a `description`, following the existing `SHARING_*` block. After
editing, regenerate the docs with `./gen_config_docs.sh` so
`docs/CONFIG_REFERENCE.md` and `config.example.yml` never drift.

If an endpoint or response model changes, regenerate `CheckCheck/openapi.json`
and then the frontend types (`bun run postinstall` in `CheckCheck/frontend`).

## 1. Orientation: how notifications work today

### 1.1 The three existing notification types

Defined in
[`model/notification.py:30-36`](../../CheckCheck/backend/checkcheckserver/model/notification.py):

| Type | Meaning | Emitted at | Recipient |
|---|---|---|---|
| `card_shared` | A card was shared with you, instant-share mode | [`api/share_ops.py:125`](../../CheckCheck/backend/checkcheckserver/api/share_ops.py) | the new collaborator |
| `card_invited` | You were invited to a card, invite mode (`SHARING_REQUIRE_INVITE_ACCEPT`) | [`api/share_ops.py:104`](../../CheckCheck/backend/checkcheckserver/api/share_ops.py) | the invitee |
| `public_link_opened` | Someone opened your public link | [`api/access.py:348`](../../CheckCheck/backend/checkcheckserver/api/access.py) | the card owner |

All three carry a `cl_id` and a free-form JSON `payload` whose known keys are
`actor_display_name` and `checklist_name` (see the renderer in
[`components/NotificationBell.vue:139-156`](../../CheckCheck/frontend/components/NotificationBell.vue)).
The payload never holds secrets, and it must stay that way.

Candidate types deliberately **not** added by this plan: `invite_accepted`
(owner learns the invitee accepted), `card_unshared`, `item_mentioned`. A future
`reminder_due` is covered in section 8.

### 1.2 The single emission seam

[`db/notification.py:105`](../../CheckCheck/backend/checkcheckserver/db/notification.py)
`emit_notification()` is the only place a `Notification` row is created. It
persists the row and pushes an SSE nudge (`upd_prop="notification"`) to the
recipient. Its own docstring names it as the hook point for this sub-project.
**Everything in this plan hangs off that one function.** No call site of
`emit_notification` needs to change.

### 1.3 Facts that shape the design

- **`User.email` is `Optional`.** OIDC users can arrive without an email claim.
  `is_email_verified` exists on the model but is set to `False` at registration
  and never flipped anywhere in the codebase. Any send path must handle "no
  address" as an ordinary, non-error outcome.
- **The server runs a single uvicorn process**
  ([`main.py:84-99`](../../CheckCheck/backend/checkcheckserver/main.py)), so no
  cross-process coordination is needed today. Use `FOR UPDATE SKIP LOCKED` on
  Postgres anyway as cheap insurance if someone ever runs replicas.
- **In-process background tasks are already an established pattern here**:
  [`routes_sync_notification.py:353-361`](../../CheckCheck/backend/checkcheckserver/api/routes/routes_sync_notification.py)
  starts `asyncio.create_task` loops from a router lifespan and cancels them on
  shutdown. The email dispatcher follows exactly this shape.
- **`SERVER_PUBLIC_URL`** is the single source of truth for every absolute URL
  the server builds. All email links must come from it. Never reconstruct a URL
  from request headers.
- **Feature gating** reaches the client through `GET /api/public-config`
  ([`routes_public_config.py`](../../CheckCheck/backend/checkcheckserver/api/routes/routes_public_config.py))
  and the `publicConfig` Pinia store.
- **Online-only surfaces**: notification settings are read/written over the
  network only. Follow the WI-12 pattern (`assertOnline` plus `useConnectivity`),
  never queue them in the offline outbox.

## 2. Decisions already settled with the maintainer

1. **Preferences are stored as JSON**, one row per user, not as per-type columns.
   Adding a notification type or a channel must not require a migration.
2. **Send path is an outbox table plus one in-process dispatcher loop**, started
   from a lifespan, on the same 30s-tick-plus-nudge pattern as the SSE listener.
   No separate process, no broker, no deployment change. Rationale: FastAPI
   `BackgroundTasks` cannot use `yield` dependencies since FastAPI 0.106 (this
   repo pins `fastapi<0.119`), loses queued mail on any restart, has no retry or
   visibility, and structurally cannot express the three delayed behaviours we
   need (suppress-if-read, coalescing, throttling). The date-reminder feature
   needs the same due-work loop next session regardless.
   **A separate worker process was considered and rejected**, deliberately, not
   by omission. It would buy blast-radius isolation, safe multi-replica scaling
   and protection from blocking code, none of which apply: the server runs a
   single uvicorn process, `aiosmtplib` is async with a timeout, and
   `FOR UPDATE SKIP LOCKED` covers replicas anyway. It would cost the
   single-container deployment story, since every existing user would have to add
   a service to their compose file on upgrade, and it saves no code because the
   outbox table and its locking are needed either way. The decision is cheap to
   reverse later: `drain_once()` is a plain function taking a session, so a
   `notify/worker.py` entrypoint plus a `NOTIFY_DISPATCH_IN_PROCESS: false` flag
   is about 20 lines whenever someone actually needs it. Do not re-open this
   without a concrete trigger (multiple replicas in production, or mail volume
   large enough to matter).
3. **Clicking the card link in an email marks the notification read**, but the
   marking happens in the SPA after the card actually opens, never in a redirect
   endpoint. Mail security scanners pre-fetch links and would otherwise mark
   everything read before the human sees it.
4. **Webhooks are a per-user setting behind an admin master switch** (default
   off), with a private-IP guard. Last chunk, droppable.
5. **Sending a public link to an email address is in scope.** Inviting a person
   who has no account yet is **out of scope** (needs a pending-invite-by-email
   identity concept and interacts badly with OIDC-only instances). Noted as a
   follow-up in section 8.

## 3. Data model

### 3.1 `user_notification_settings` (new table, chunk E3)

One row per user, created lazily on first read or write.

```python
class UserNotificationSettings(TimestampedModel, table=True):
    __tablename__ = "user_notification_settings"
    user_id: uuid.UUID = SQLField(primary_key=True, foreign_key="user.id", ondelete="CASCADE")
    # {"<notification_type>": {"<channel>": "<mode>"}}
    # e.g. {"card_shared": {"email": "immediate"}, "public_link_opened": {"email": "off"}}
    prefs: dict = SQLField(default_factory=dict, sa_column=Column(JSON))
    # IANA name, e.g. "Europe/Berlin". Used for email timestamps today and by the
    # date-reminder feature next session.
    timezone: Optional[str] = SQLField(default=None, max_length=64)
    # Per-user webhook target (chunk E6). Null = no webhook.
    webhook_url: Optional[str] = SQLField(default=None, max_length=2048)
    unsubscribe_secret: str  # random, per user; rotated when the user asks
```

- **Channels**: `in_app`, `email`, `webhook`.
- **Modes**: `off`, `immediate`, `hourly`, `daily`. Not every channel supports
  every mode (`in_app` is `off` or `immediate`; `webhook` likewise). Validate.
- **A missing key means "use the instance default"**, resolved in code. This is
  what makes a new notification type work without a migration and without
  backfilling every user row.
- `in_app` is part of the same matrix so a user can mute the bell too, which is
  free once the resolver exists.

### 3.2 `notification_outbox` (new table, chunk E2)

One row per (notification, channel) delivery attempt.

```python
class NotificationOutbox(TimestampedModel, table=True):
    __tablename__ = "notification_outbox"
    id: uuid.UUID
    user_id: uuid.UUID          # FK user, CASCADE. The recipient.
    notification_id: Optional[uuid.UUID]  # FK notification, CASCADE. Null for non-feed mail (test mail, public-link share).
    channel: str                # "email" | "webhook"
    status: str                 # "pending" | "sent" | "failed" | "cancelled"
    not_before: datetime        # naive UTC. Enables the suppress/coalesce delay.
    attempts: int = 0
    last_error: Optional[str]
    dedupe_key: Optional[str]   # unique-ish key for coalescing, indexed
    payload: dict               # everything the renderer needs, snapshotted at enqueue time
```

Index on `(status, not_before)`, which is the dispatcher's only query.

**Why snapshot the payload** rather than re-reading the notification at send
time: the card may have been renamed, unshared or tombstoned in the meantime, and
re-reading it inside the dispatcher would either leak post-revocation state or
crash. Snapshot at enqueue, when the access check has just passed.

**Retention**: rows in `sent` state older than `NOTIFY_OUTBOX_RETENTION_DAYS`
are pruned by the same loop. `failed` rows are kept longer so an operator can
see what broke.

## 4. The dispatcher

New module `checkcheckserver/notify/` with:

- `transports.py`: the channel abstraction. `EmailTransport` protocol with
  `smtp`, `console` (logs the message), `file` (writes `.eml` into a directory)
  and `null` implementations, selected by config. `console`/`file` exist so local
  dev and E2E never need a mail server.
- `render.py`: builds subject plus `text/plain` and `text/html` bodies per
  notification type. Multipart, `List-Unsubscribe` header, stable
  `Message-ID`, and `References` keyed on the card id so a mail client threads
  everything about one card together.
- `prefs.py`: `resolve_mode(user, type, channel) -> Mode`. Order of precedence:
  instance hard-cap (admin disabled the type or channel entirely) beats user
  preference beats instance default beats code default.
- `outbox.py`: `enqueue()`, `drain_once()`, `prune_once()`.
- `dispatcher.py`: the lifespan loop. `while True: await drain_once(); await
  wait_for(nudge_event, timeout=tick)`. Cancelled on shutdown like the SSE tasks.

**`drain_once()` is a plain async function taking a session.** Tests call it
directly and assert on the transport's captured messages. No test ever starts the
loop.

### 4.1 Suppression and coalescing rules

These are the behaviours that make the feature pleasant rather than annoying.
Implement them in `drain_once()`, at the moment a row becomes due:

1. **Already read** wins. If the linked `notification.read_at` is set, mark the
   outbox row `cancelled` and send nothing. This is why `not_before` defaults to
   `now + NOTIFY_EMAIL_SUPPRESS_WINDOW_SECONDS` (default 120) for `immediate`
   mode: a user who is looking at the app right now gets no mail.
2. **Coalescing.** Rows sharing a `dedupe_key` that are due at the same time
   collapse into one message ("Anna shared 5 cards with you"). The key is
   `f"{user_id}:{type}:{actor_id}"` for share events. This is what stops a
   30-person group share turning into 30 separate mails per person.
3. **Throttling.** `public_link_opened` is triggerable by anyone holding the
   link, so it is rate-limited per (card, user) to at most one mail per
   `NOTIFY_PUBLIC_LINK_THROTTLE_MINUTES` (default 60), and its email default is
   `off` even when the type is enabled. Reloading a public link in a loop must
   not flood the owner's inbox.
4. **No address, no send.** A user with `email is None` produces no outbox row at
   all (do not enqueue and then fail). Log at debug, not warning.
5. **Verification.** `NOTIFY_EMAIL_REQUIRE_VERIFIED` defaults to `false`, because
   in a self-hosted instance addresses come from OIDC or an admin and are
   trusted. When true, an unverified address is skipped.

### 4.2 Retry policy

Exponential backoff on transient failures (connection refused, 4xx SMTP), capped
at `NOTIFY_MAX_ATTEMPTS` (default 6), after which the row goes `failed` and stays
for inspection. Permanent failures (5xx SMTP, invalid address) go straight to
`failed` without retrying. Never retry inside a request.

| Method | Path | Chunk | Notes |
|---|---|---|---|
| `GET` | `/api/user/me/notification-settings` | E3 | Returns the resolved matrix (effective mode per type per channel) plus which entries are admin-locked, plus timezone. The UI must be able to show "your admin disabled this". |

## 7. Session chunks

Each chunk is one session. Do not start the next one in the same session even if
there is time left: finish, test, write the handoff.

### E1: config, transports, and the mail test harness

**Goal:** the server can send an email, and tests can observe it, but nothing
sends one yet.

- Full config block from section 5 (webhook and public-link-email settings can
  come later, but adding them now avoids a second `gen_config_docs.sh` pass).
- Startup validation: `EMAIL_ENABLED` with no `EMAIL_FROM_ADDRESS` or, for the
  `smtp` transport, no `EMAIL_SMTP_HOST`, must fail loudly at boot rather than
  silently swallowing mail at runtime.
- `notify/transports.py` with all four transports. Add `aiosmtplib` to
  `pyproject.toml` and sync **both** venvs (pdm-managed `backend/.venv` for the
  dev server, uv root `.venv` for pytest).
- `email_enabled` on `GET /api/public-config`.
- Test harness: a pytest fixture giving a capturing transport, plus one real
  end-to-end SMTP test against an in-process `aiosmtpd` server so the SMTP code
  path is genuinely exercised and not just mocked.

**Tests:** transport selection per config, startup validation failures, multipart
structure, headers, `aiosmtpd` round trip, `console` and `file` transports.

### E2: outbox table and dispatcher loop

**Goal:** durable queued delivery with retry, driven by a lifespan task.

- Alembic revision `0013` for `notification_outbox`.
- `notify/outbox.py`: `enqueue`, `drain_once`, `prune_once`, with `FOR UPDATE
  SKIP LOCKED` on Postgres.
- `notify/dispatcher.py`: the lifespan loop plus the nudge event, wired the same
  way as the SSE listener, cancelled cleanly on shutdown.
- `POST /api/user/me/notification-settings/test-email` as the first real
  producer, so the whole path is exercisable by hand from day one.
- Retry, backoff, dead-letter, retention pruning.

**Tests:** enqueue then drain sends once; transient failure retries with growing
backoff; `NOTIFY_MAX_ATTEMPTS` reaches `failed`; permanent failure does not
retry; `not_before` in the future is not picked up; concurrent drains do not
double-send; pruning removes the right rows and keeps `failed`; loop starts and
cancels cleanly.

### E3: preference model, resolution, and API

**Goal:** users have preferences; nothing consumes them yet.

- Alembic revision `0014` for `user_notification_settings`, lazily created rows,
  per-user `unsubscribe_secret`.
- `notify/prefs.py` resolver with the precedence from section 3.1, plus
  validation of which modes each channel accepts.
- `GET` and `PUT /api/user/me/notification-settings`, returning effective modes
  and admin-locked flags.
- Timezone field, validated against the IANA database.

**Tests:** the full resolution matrix (unset key falls back to instance default,
user override wins, admin cap beats user override); `PUT` rejects a capped mode;
`PUT` rejects an unknown type, channel, mode or timezone; a brand new user with
no row gets sane defaults; a new notification type added in code needs no
migration and no backfill.

### E4: wiring, rendering, suppression, unsubscribe

**Goal:** the three real notification types actually send mail, correctly.

- `emit_notification()` fans out to `enqueue()` for every channel whose resolved
  mode is not `off`. **This is the only change to existing call sites, and there
  should be none.**
- `notify/render.py` templates for all three types, in both `full` and `minimal`
  content modes, text and HTML.
- Deep links built from `SERVER_PUBLIC_URL` as `/?card={cl_id}&n={notification_id}`.
- Suppression, coalescing and throttling from section 4.1.
- Hourly and daily digest assembly.
- Unsubscribe endpoint plus `List-Unsubscribe` header.
- Per-user hourly send cap.

**Tests:** one test per type end to end through the capturing transport; no mail
when the mode is `off`; no mail and no row when the user has no address; mail
suppressed when the notification was read inside the window; a group share to N
users produces N mails, not N squared; five shares from one actor coalesce into
one mail; `public_link_opened` respects the throttle; `minimal` mode leaks
neither card name nor actor name; unsubscribe with a valid token flips exactly
one type to `off`; forged, tampered and expired tokens are rejected; digests
collect the right window and empty windows send nothing.

### E5: frontend settings UI and read-on-open

**Goal:** the user can see and change all of this, and email links behave.

- `NotificationSettingsModal.vue`, opened from the user menu in
  [`Navbar.vue:110-130`](../../CheckCheck/frontend/components/Navbar.vue) next to
  the existing "API keys" entry, following the `ApiKeysModal` pattern
  (declarative `v-model:open` so it cannot double-dialog).
- A per-type row with a channel column each for in-app and email, mode select,
  admin-locked entries rendered disabled with a reason, timezone picker, and a
  "Send test email" button with success and failure feedback.
- Hidden entirely when `email_enabled` is false; the in-app column still shows.
- Online-only: `assertOnline` plus a `useConnectivity` notice, never queued in
  the offline outbox.
- Read-on-open: `pages/index.vue` reads the `n` query parameter and calls
  `notificationStore.markRead(n)` **after** the card overlay has rendered, then
  strips the parameter from the URL.

**Tests:** unit specs for the resolution display logic and the query-parameter
handler; E2E for opening the modal, changing a mode and seeing it persist across
reload, the disabled state when the admin capped a type, the offline notice, and
the `?card=&n=` deep link marking exactly that notification read.

### E6: webhooks, public link by email, feed retention

**Goal:** the optional extras. Droppable without harming E1 to E5.

- Webhook channel: per-user `webhook_url`, admin master switch, generic JSON
  payload, SSRF guard rejecting private and loopback ranges unless
  `NOTIFY_WEBHOOK_ALLOW_PRIVATE_IPS`, short timeout, same retry policy, plus a
  "send test webhook" action.
- `POST /api/checklist/{id}/public-share/email`: mails an existing public link to
  an address, owner only, feature-flagged, rate-limited per user per hour, with
  the address never echoed back in an error (no user enumeration). Add a small
  "send by email" field in `ShareModal`.
- Feed retention pruning of the `notification` table via
  `NOTIFY_FEED_RETENTION_DAYS`, in the same loop.

**Tests:** webhook posts the expected body and honours the master switch;
`http://169.254.169.254` and `http://127.0.0.1` are refused by default and
allowed when the flag is on; DNS-rebinding style hostnames resolving to private
IPs are refused too; public-link mail requires ownership plus both flags and
respects the rate limit; feed pruning keeps unread rows inside the window.

## 8. Explicitly out of scope, and what comes next

- **Date-based reminders** ("notify me about that checklist at date"), the
  maintainer's next session. It reuses this infrastructure directly: a
  `scheduled_notification` table whose due rows are picked up by the same
  dispatcher loop, emitting a new `reminder_due` notification type through
  `emit_notification`. The per-user `timezone` field in section 3.1 exists
  specifically so that feature does not need another migration. Open questions
  for it: who gets the reminder (owner only, or all collaborators), and what
  happens to a pending reminder when the card is deleted or the user's access is
  revoked.
- **Inviting a person who has no account yet** by email address. Needs a
  pending-invite record keyed on an address, matched at registration, and it
  conflicts with OIDC-only instances where the server does not control signup.
- **Email address verification and change flow.** `is_email_verified` stays dead
  code for now. The plumbing built here (transports, outbox, signed tokens) is
  most of what it would need.
- **Web push.** The channel abstraction accommodates it, but it needs VAPID keys
  and service-worker work that has nothing to do with this plan.
- **Per-card mute** ("stop notifying me about this card"). Worth doing, but it
  belongs with the reminder feature, where it becomes genuinely necessary.
