# Plan: notification rework (acting on the review findings)

**Status:** in progress (written 2026-08-03). N1 to N4 done, N5 not started.

**Scope:** every finding in [`NOTIFICATIONS_FINDINGS.md`](NOTIFICATIONS_FINDINGS.md), the review of
the email (E1 to E7), date-reminder (R1 to R4) and system-notification (P1, P2) chunks on
`feature/email-notifications`. This document turns that findings list into five session-sized
chunks. It does not restate the analysis: each chunk links back to the finding it closes, and the
finding is the specification.

Nothing here changes the shape of the notification architecture. The preference matrix, the outbox,
the retry policy and the four notification types are all unchanged. This is a hardening pass on the
push channel plus a small amount of email polish.

## 0. Standing rules (unchanged from the three feature plans)

- Every behaviour change gets a backend test (`CheckCheck/backend/tests/`), run on **both**
  `./run_backend_tests_with_sqlite.sh` and `./run_backend_tests_with_postgres.sh` (full suite, not
  just the new file). Postgres is the production target; SQLite is local-dev only.
- Anything a user clicks gets vitest and/or Playwright coverage.
- No em dashes or en dashes anywhere in docs, comments, commit messages or UI copy.
- Schema changes are real autogenerated Alembic revisions on top of the current head
  (`0016_push_subscription`). **No chunk in this plan needs one**, which is deliberate: every fix
  here is behavioural, and if one starts to look like it wants a column, stop and re-read the
  finding first.
- New settings go into `config.py` with a `title` and `description`, then `./gen_config_docs.sh`.
  Only chunk N3 adds one, and only if the maintainer wants the payload budget configurable.
- Any endpoint or response-model change means regenerating `CheckCheck/openapi.json` and the
  frontend types (`bun run postinstall`). Chunks N2 and N4 both change registration responses.
- End every session by overwriting `NEXT_SESSION.md` with a cold-start prompt and updating the
  progress table in section 9 of this document.
- **The maintainer commits, nobody else.** A session leaves its work in the working tree: no
  `git add`, no `git commit`, no `git push`. Report what changed and which files are dirty instead.

## 1. Decisions settled before chunking

These answer section 14 of the findings document. They are settled; a chunk that wants to revisit
one should say so in its handoff rather than quietly diverge.

| # | Question | Decision |
|---|---|---|
| 1 | Scope of the push SSRF fix | **Public-address guard only.** Reuse the webhook channel's resolve-then-judge logic: require `https://` and a public unicast host. No operator-configurable allowlist of push-service hosts: it adds a setting and docs, and it breaks a self-hosted push relay for no gain over the guard. |
| 2 | What a 413 should do | **Fail the outbox row, and prevent the case.** Delete the subscription only on 404/410; every other 4xx fails the row as permanent (kept for inspection) and touches no subscription. Separately, add a length budget to the push payload so `full` content mode plus a long card name plus a long note cannot reach a push service's 4 KB limit in the first place. |
| 3 | What logout does to a push subscription | **Unsubscribe and delete.** Explicit logout unsubscribes the browser and `DELETE`s the server row. A user who logs out and back in re-enables push; that is the accepted cost of closing the shared-device lock-screen disclosure (finding 5.2). |
| 4 | Re-binding an endpoint owned by another account | **No.** A registration for an endpoint that belongs to a different user is a **409**, and the browser resubscribes to get a fresh endpoint. Given decision 3 the legitimate shared-browser case is already handled by the logout unsubscribe, so re-binding buys nothing and costs a silent cross-account takeover. |
| 5 | Sanitise the subject or constrain `CheckList.name` | **Sanitise at subject-build time.** Constraining the model is a wider change with sync and migration implications for a problem that only exists in one output context. Not asked of the maintainer, so flagged here as an assumption: if "a card name is one line" is a rule you want anyway, that is a separate change and this fix stays correct underneath it. |
| 6 | Ordering | **Email-only fixes first, then push.** `NOTIFY_PUSH_ENABLED` is `false` by default, so an email-only instance can ship after chunk N1. The push chunks (N2 to N5) are the release gate for turning push on, not for the release itself. |

  [`notify/render.py:141-197`](../../CheckCheck/backend/checkcheckserver/notify/render.py), and

  matching what `unsubscribe_url()` already does with the same value.
- **Finding 12, truncated comment** in
  [`notify/reminders.py:76`](../../CheckCheck/backend/checkcheckserver/notify/reminders.py). Already
  fixed in the working tree ("... or whose access is revoked"), uncommitted. Fold it into this
  chunk's commit rather than leaving it loose.

**Tests:**

- `tests_email_templates.py`: a card name containing `\n` (and a reminder note containing `\r\n`)

- `tests_notification_outbox.py` (or wherever the retry classification lives): a transport raising

- New coverage in `tests_public_link_email.py` or a sibling: a user who sends ten public-link
  invitations still receives a `card_shared` notification mail within the same hour, with

- Unsubscribe: a token round-trips through the rendered form action unchanged.

## 4. N2: the push endpoint guard

**Goal:** the push channel stops being an unguarded SSRF primitive (finding 1). This is the largest
single chunk and the one with the most careful test surface, so it gets a session to itself.

**Changes:**

- **Extract the address judgement.** `_is_public_address` and `_resolve`
  ([`notify/webhooks.py:103-137`](../../CheckCheck/backend/checkcheckserver/notify/webhooks.py))
  are channel-agnostic. Move them into a small shared module (`notify/net_guard.py` is the obvious
  name) and have `webhooks.py` import them, so the two channels cannot drift. Keep
  `check_webhook_target` where it is: the pinned-URL rewrite is webhook-specific.
- **Guard at registration.** In `register_push_subscription`
  ([`routes_notification_settings.py:513-579`](../../CheckCheck/backend/checkcheckserver/api/routes/routes_notification_settings.py)),
  before the upsert: parse the endpoint, require scheme `https`, resolve the host, and reject unless
  every resolved address is public unicast. A refused endpoint is a **400** with a message that says
  what was wrong without echoing resolution detail back to the caller (the resolution result is an
  information leak in its own right; log it at debug, do not return it).
- **Re-check at delivery.** In `_send_sync`
  ([`notify/push.py:133-153`](../../CheckCheck/backend/checkcheckserver/notify/push.py)), re-run the
  same judgement before handing the endpoint to `pywebpush`, for the rebinding reason the webhook
  guard documents (a host that resolved publicly at registration can resolve privately later).
  A refusal here is a `PermanentPushError`; **note that under N3's classification that must fail the
  row, not delete the subscription**, so if N3 has not landed yet, raise a distinct error type
  (`PushEndpointRefused`) and handle it explicitly in `_deliver_push` rather than relying on the
  `PermanentPushError` branch. Say which order the two chunks landed in, in the handoff.
- **`pywebpush` follows redirects and this guard cannot stop it.** The webhook channel closes the
  TOCTOU by connecting to the address it judged; `pywebpush` gives us no such hook. Document this
  honestly in the module docstring: the guard is resolve-then-judge without pinning, a redirect to a
  private address is still reachable, and closing that would mean replacing `pywebpush`'s transport.
  Do not claim parity with the webhook guard in a comment when there is none.

**Tests** (`tests_notification_push.py`, mirroring `tests_notification_webhooks.py`'s cases, which
are the model to copy):

- Registration refuses `http://` (any host), `http://127.0.0.1:5432/`, a hostname resolving into
  RFC 1918, and `169.254.169.254`. Each is a 400 and writes no row.
- Registration accepts a public `https://` endpoint (resolver stubbed, as the webhook tests do).
- Delivery refuses an endpoint that resolves privately at send time even though the row exists,
  without deleting the subscription.
- The refusal path never calls `pywebpush.webpush` (assert on the monkeypatched sender).

(Gap 2.)

**Done when:** both backend suites are green, `CheckCheck/openapi.json` and the frontend types are
regenerated for the new 400, and the docstring states the redirect limitation.

## 5. N3: push delivery correctness

**Goal:** a server-side misconfiguration can no longer mass-delete every subscription on the
instance (finding 2), and the misconfiguration that causes it fails at boot instead (finding 9).

**Changes:**

- **Narrow the delete.** In `_send_sync`'s classification
  ([`notify/push.py:154-171`](../../CheckCheck/backend/checkcheckserver/notify/push.py)), keep
  404/410 as "this subscription is gone" and introduce a second permanent error for everything else
  ("the push service refused this request"). Two distinct exception types, not a flag: the two
  events have different consequences and the type is what carries that.
- **Act on the distinction.** In `_deliver_push`
  ([`notify/outbox.py:556-568`](../../CheckCheck/backend/checkcheckserver/notify/outbox.py)), only
  the gone-subscription error deletes a row. A refusal fails the **outbox row** as permanent
  (`failed`, kept for inspection, subscription untouched) and logs at warning, not debug: a 401 from
  a push service is the operator's cue that VAPID is broken, and it currently produces one debug
  line per silently deleted device.
- **Payload budget** (decision 2). Give `push_payload`
  ([`notify/render.py:395`](../../CheckCheck/backend/checkcheckserver/notify/render.py)) a byte budget (the Web Push practical limit
  is ~4 KB after encryption; budget the plaintext JSON well under it, ~3 KB) and truncate the body,
  then the title, with an ellipsis, before serialising. A long card name plus a long reminder note
  in `full` content mode is an ordinary case, not an attack, and it should arrive shortened rather
  than fail. Module constant, not a config setting, unless the maintainer asks otherwise.
- **Finding 9, VAPID pair correspondence.** In `validate_vapid_keys`
  ([`notify/push.py:227-255`](../../CheckCheck/backend/checkcheckserver/notify/push.py)), derive the
  public point from the loaded private scalar and compare it to the configured public key. This is
  the check the existing error message already claims to perform ("are not a usable key pair"). A
  mismatch becomes a startup failure instead of a silent mass-unsubscribe on the first notification.

**Tests:**

- `_send_sync` classification: 404 and 410 give the gone error; 401, 403, 400 and 413 give the
  refusal error; 429 and 500 stay transient; no response stays transient. This **replaces** the
  current `test_send_sync_classifies_push_service_status_codes` assertions, which encode the
  behaviour being fixed.
- `_deliver_push` with a subscription whose service answers 401: the row ends `failed`, the
  subscription **still exists**. Same for 413. (Gap 3.)
- Mixed case still works: one subscription 410s and one succeeds, row ends `sent`, only the dead one
  is gone.
- Payload budget: a card name plus note far over the budget produces a payload under it, with the
  title still present and identifiable.
- Boot: two individually valid but unrelated VAPID halves raise at startup;
  `test_boot_accepts_a_real_vapid_key_pair` still passes with a real pair. (Gap 5.)

**Done when:** both backend suites are green and no code path deletes a subscription for a reason
other than 404/410.

## 6. N4: push registration ownership and limits

**Goal:** registering a subscription cannot take one away from another account (finding 3), and one
account cannot register an unbounded number of them (finding 4).

**Changes:**

- **409 on a foreign endpoint** (decision 4). In `upsert`
  ([`db/push_subscription.py:42-99`](../../CheckCheck/backend/checkcheckserver/db/push_subscription.py)),
  stop re-assigning `user_id`. If `get_by_endpoint` returns a row owned by someone else, raise a
  typed error the route turns into a **409** with a message the client can act on ("this device is
  registered to another account; sign out there or clear site data"). An endpoint owned by the
  caller keeps upserting exactly as it does today, which is the normal
  re-register-on-every-page-load path and must not regress.
- **Per-user cap** (finding 4). A module constant in the `MAX_PENDING_PER_USER` style
  (`MAX_SUBSCRIPTIONS_PER_USER = 15`), enforced in `register_push_subscription` using the existing
  `count_for_user`. Over the cap, evict the oldest `last_seen_at` row rather than failing the call:
  a user replacing devices should not have to go and prune a list they may not know exists. Log the
  eviction. (Failing with a 409 is the alternative the finding suggests; eviction is chosen because
  the device list is a cache of browsers, not user-authored data, and a dead browser's row is the
  natural thing to lose.)
- **Finding 8, delete by primary key.** `_deliver_push` holds `subscription.id`; use it. Replace
  `delete_by_endpoint` (no other caller) with a delete by id in
  [`db/push_subscription.py:119-122`](../../CheckCheck/backend/checkcheckserver/db/push_subscription.py).
  With the 409 above the race is mostly gone, but the precise call is free.

**Tests:**

- User B registering an endpoint that belongs to user A gets a 409, and A's row is unchanged (owner,
  keys, `id`). This is the register-side twin of the existing
  `test_delete_only_removes_the_owners_own_subscription`. (Gap 1.)
- Re-registering the caller's own endpoint still upserts in place: one row, `last_seen_at` moved,
  keys updated.
- Registering past the cap evicts exactly the oldest-`last_seen_at` row and leaves the count at the
  cap. (Gap 4.)
- A dead subscription is deleted by id: two rows for the same user, one 410s, the other survives
  with its id intact.

**Done when:** both backend suites are green and `openapi.json` plus frontend types are regenerated
for the new 409.

## 7. N5: frontend push lifecycle

**Goal:** the browser's idea of its subscription is reconciled against the server's, and logging out
takes the device's push with it (finding 5). This is the chunk with the most user-visible surface
and the only one that needs Playwright.

**Changes:**

- **Reconcile in `refresh()`**
  ([`composables/usePushSubscription.ts:71-86`](../../CheckCheck/frontend/composables/usePushSubscription.ts)).
  After `listPushSubscriptions()`, compare `currentEndpoint` against the returned device list. If the
  browser holds a subscription the server does not know about, unsubscribe it locally and clear
  `currentEndpoint`, so the state the UI drives off is the reconciled one rather than raw browser
  state. Drive `isSubscribedHere` off that reconciled value, not `!!currentEndpoint`.
- **Un-dead-end the Enable button**
  ([`components/NotificationSettingsModal.vue:273`](../../CheckCheck/frontend/components/NotificationSettingsModal.vue)).
  With reconciliation in place the button is enabled again for the new user. Surface N4's 409 as a
  readable message next to the button rather than a generic failure toast: a user on a shared
  browser needs to be told what happened, and this is the one path where the fix is "try again"
  (the local unsubscribe frees the endpoint).
- **Check the VAPID key on enable.** `enable()` currently reuses an existing `getSubscription()`
  result without comparing its `applicationServerKey` to the server's current key. Compare, and
  unsubscribe-then-resubscribe on a mismatch. Without this, a key rotation leaves devices subscribed
  to a key the server no longer signs with, which is exactly the 403 N3 now turns into a failed row
  and a confused operator.
- **Logout hygiene** (decision 3). Next to `clearLocalState()` in
  [`components/Navbar.vue:174`](../../CheckCheck/frontend/components/Navbar.vue), unsubscribe the
  browser's push subscription and `DELETE` the server row. Best-effort and non-blocking, in the same
  `.catch(() => {})` spirit as the existing call: logout must not hang on a push service. Consider
  ordering the `DELETE` before the local unsubscribe so the server row goes first while the session
  cookie is still valid.
- **Account-switch safety net.** `reconcileAccount()`
  ([`utils/localSnapshot.ts:148-197`](../../CheckCheck/frontend/utils/localSnapshot.ts)) already
  handles "someone else logged in on this browser" for the snapshot and outbox. Add the local push
  unsubscribe there too, for the case where the previous session ended without a clean logout
  (crash, cleared tab, expired cookie). `refresh()`'s reconciliation covers the settings dialog;
  this covers the lock screen.
- **Finding 10, `?card=` deep link.** UUID shape check on `link.cardId` before
  `ctx.replace({ path: '/card/' + link.cardId })` in
  [`utils/notificationDeepLink.ts:101`](../../CheckCheck/frontend/utils/notificationDeepLink.ts).
  Fall back to the board rather than routing to a crafted path.

**Tests:**

- **vitest, new `tests/unit/usePushSubscription.spec.ts`** (gap 8, the composable currently has no
  unit test at all; `tests/unit/push.spec.ts` covers only the pure helpers). Mock the store,
  `navigator.serviceWorker` and `Notification` the way the E2E specs already stub them. Cases:
  `refresh()` with a browser subscription absent from the server list unsubscribes locally and
  leaves the Enable button available (gap 9); `refresh()` with a matching row leaves it alone;
  `enable()` on a key mismatch resubscribes; `enable()` receiving a 409 sets a readable error;
  `disable()` clears both sides.
- **Playwright**, in `tests/e2e/notification-settings.spec.ts` next to the existing
  `P2 push notifications` block: log in as A, enable push, log out, log in as B on the same context,
  open the settings dialog, and assert the Enable button is usable and the device list is empty
  (gap 9). And: enable, log out, assert the server row is gone (gap 10).
- Deep link: a non-UUID `?card=` value routes to the board and does not throw.

**Done when:** the full vitest suite and `./run_e2e_tests.sh` are green (allowing for the known

### N4 notes and deviations

- **The ownership check is in the store, the status code is in the route.** `upsert` raises
  `EndpointOwnedByAnotherUser` (a plain exception in `db/push_subscription.py`) and never re-assigns
  `user_id` on a row it did not already own. Both branches raise: the `existing is not None` one and
  the `IntegrityError` race one, where losing the insert race to another account is the same takeover
  arriving a millisecond later. The route is the only caller and turns it into the 409.
- **The cap is enforced after the upsert, not before it.** `_enforce_subscription_cap` runs once the
  row is written and evicts while the count is *over* the cap. Checking first would have needed a
  second query to tell "this is a new device" from "this is the same device re-registering", because
  only the first grows the count. Enforcing afterwards gets both cases right for free: a refresh
  evicts nothing, and the row just written always has the newest `last_seen_at`, so it can never
  evict itself. It is a `while` rather than a single delete so that lowering the constant prunes an
  account that is already over it, instead of leaving it stuck one device above the new limit.
- **`MAX_SUBSCRIPTIONS_PER_USER = 15` lives next to the queries that enforce it**, in
  `db/push_subscription.py`, the `scheduled_notification.MAX_PENDING_PER_USER` precedent. The route
  reads it through the module (`push_subscription_db.MAX_SUBSCRIPTIONS_PER_USER`) rather than
  importing the name, which is what the rest of that file already does with this module.
- **Eviction is user-scoped by construction.** `delete_oldest_for_user` takes the user id and orders
  by `last_seen_at` within that user, so making room for a new device cannot take one away from
  somebody else. It returns the row it deleted so the caller can log which one went and when it was
  last seen; that is an `info` line, not `debug`, because it is the only trace of a device
  disappearing for a reason that is not 404/410.
- **The invariant N3 established is intact.** Nothing new deletes a `push_subscription` row: the
  drain still deletes only on `PushSubscriptionGone`, and the two deliberate user-facing paths are
  the owner's own `DELETE` and this cap eviction.
- **`delete_by_endpoint` was replaced, not supplemented.** It had exactly one caller, so it is now
  `delete_by_id` and `_deliver_push` passes the id it was already logging.
- **The endpoint has two different 409s now**, and that is fine: "this instance does not send push
  notifications" and "this device is already registered to another account" are both conflicts with
  the server's state, and the detail strings tell them apart. The second is written to be shown to a
  user, because unlike the first there is something they can do about it (sign out on the other
  account, or clear this site's data). N5 owns actually surfacing it.
- **`openapi.json` carries only the endpoint description again.** FastAPI does not add a response
  entry for a status raised through `HTTPException`, and no response model changed, so the 409 is
  documented in prose exactly as N2's 400 is. The frontend types were regenerated and no committed
  frontend file moved. The version line a test run stamps into the file was put back, as before.
- **The tree was clean at the start of this session**, unlike what the N4 handoff expected: the
  maintainer had already committed N2 and N3 as `2df1e23`. Nothing about the work changed, but the
  dirty files listed at the end of this session are N4's alone.

### N3 notes and deviations

- **The error hierarchy, and why it is shaped that way.** `PermanentPushError` stopped being a thing
  anything raises: it is now the base of `PushSubscriptionGone` (404/410, the only error that deletes
  a device) and `PushEndpointRefused` (the guard's refusal from N2, plus every other 4xx). N2's
  `PushEndpointRefused` was deliberately *not* a `PermanentPushError` so that N3 could not
  re-introduce the delete by rearranging handlers; folding it back under a common base keeps that
  property for a different reason. `_deliver_push`'s delete clause is keyed on the exact
  `PushSubscriptionGone` type and the refusal clause catches the base, so the two branches cannot be
  swapped into something destructive: catching the base first would route a gone subscription into
  the *keep it* path, never the reverse. That is the safe direction to fail in.
- **One refusal path, as the handoff asked.** The SSRF guard's refusal and a 401 from a push service
  are the same event from the row's point of view and share the branch: the outbox row ends `failed`
  with the note, no subscription is touched, and the log line is a warning. There is no third branch.
- **Transient still wins over refused.** When one device answers 503 and another 401 in the same
  attempt, the row retries (`transient_seen` is checked before `refused_seen`). Unchanged from N2 and
  deliberate: the transient device may well succeed next time, and the refused one leaves its note
  either way.
- **The payload budget needed a floor under the body.** Truncating "the body first, then the title"
  literally means a title that alone exceeds the budget empties the body, and
  `_validate_push_payload` rejects a payload with an empty body: the notification would then fail to
  queue at all, which is worse than the 413 the budget exists to prevent. So the body keeps
  `PUSH_BODY_RESERVE_BYTES` (256) and the title takes the rest. The ordering the plan asked for is
  intact (the body is the field that gets shortened first), it just cannot reach zero.
- **The budget is measured, not estimated.** `_json_cost` measures a field's escaped length in the
  serialised payload, because that is what a push service counts: one `"` in a card name costs two
  bytes and an emoji costs twelve. Costs are additive across the fields, which is what lets the split
  between title and body be computed rather than searched. The prefix length itself is a binary
  search, a dozen measurements instead of a few thousand.
- **`_push_title` still is not newline-sanitised.** N1 left it alone and so does this chunk. A
  newline in a JSON payload is not a delivery failure the way it is in a mail header, the truncation
  above does not care either, and giving push titles the email subject's `subject_line()` treatment
  would change wording that P2's frontend tests assert on. Worth doing if push copy is ever revisited;
  not worth folding into a correctness chunk.
- **VAPID correspondence is checked where the private key is already loaded.** `validate_vapid_keys`
  derives the public point from the loaded scalar (`Vapid02.from_string(...).public_key` in
  uncompressed X9.62 form) and compares bytes with the configured public key. The failure message
  names the fix (both halves from one `gen_vapid_keys.sh` run) rather than restating the check.
  `Config`'s wrapper still prefixes it with "are not a usable key pair", which is now true.
- **The E2E server's key pair was already a real pair**, so the new check changes nothing for
  `run_e2e_tests.sh`. The suite's `_TEST_VAPID_PUBLIC_KEY`/`_TEST_VAPID_PRIVATE_KEY` are a genuine
  pair too; the mismatch test needed a second pair's public half, added as
  `_OTHER_VAPID_PUBLIC_KEY`.
- **No endpoint or response model changed**, so `CheckCheck/openapi.json` carries only N2's
  description line. The version string a test run stamps into it was put back.

### N2 notes and deviations

- **N2 landed before N3.** A refused endpoint raises `PushEndpointRefused`, which subclasses
  `PushDeliveryError` **directly and not `PermanentPushError`**, and `_deliver_push` handles it in
  its own `except` clause: the outbox row fails, the subscription is left exactly where it is. That
  is deliberate rather than ordering-dependent, so N3 cannot re-introduce the delete by rearranging
  the handlers. When N3 rewrites the classification, fold this branch in: the rule it has to keep is
  "refused is permanent for the row, and never deletes a subscription".
- **What moved, and what did not.** `notify/net_guard.py` holds `is_public_address`, the async and
  blocking resolvers, the `https://` URL parse and the "every address must be public" judgement.
  `webhooks._is_public_address` is now an alias of the shared function and `webhooks._resolve` is a
  three-line wrapper that translates `HostResolutionError` into `TransientWebhookError`, so the
  channel keeps its own error vocabulary. `check_webhook_target` stayed in `webhooks.py` as planned:
  the pinned-URL rewrite and the `NOTIFY_WEBHOOK_ALLOW_PRIVATE_IPS` escape hatch are both
  webhook-specific, and `net_guard` deliberately takes no `Config` (see the next point).
- **`net_guard` may not import `config` or `log`.** `notify/push.py` is imported from inside
  `Config`'s own boot validator, so anything it imports has the same restriction it does. That is
  why the shared module uses `logging.getLogger("CheckCheck")` and has no config parameter, and why
  an operator switch to relax the judgement (if one is ever wanted for push) would have to live in
  the channel rather than here.
- **A blocking resolver was added.** Registration is async (`await loop.getaddrinfo`), but the
  delivery re-check runs inside `_send_sync`, which is already off the event loop in
  `asyncio.to_thread`. `require_public_https_target` and `require_public_https_target_sync` share
  the parse and the judgement and differ only in which resolver they call.
- **The redirect limitation is stated, not papered over.** `notify/push.py`'s module docstring now
  says in as many words that this is resolve-then-judge **without** pinning, that `pywebpush`
  resolves the name again itself and follows redirects, and that closing the window means replacing
  its transport. The webhook channel's three-step guard is not claimed here.
- **What the 400 says.** `AddressRefused`'s message is written to be safe to return verbatim ("that
  endpoint points into a private or local network"), and the addresses that caused it are logged at
  debug inside `judge_addresses` and nowhere else. A name that does not resolve is also a 400, with
  its own wording; it is not a `HostResolutionError`-shaped retry at registration, because there is
  no row to retry yet.
- **Registration is tested in-process, not over HTTP.** The live test server has
  `NOTIFY_PUSH_ENABLED` off, so every HTTP call to the register endpoint stops at the 409 before it
  reaches the guard. `tests_notification_push.py` swaps the route module's `config` in a fixture and
  calls `register_push_subscription` directly, which is the same reasoning that already keeps the
  fan-out tests out of HTTP.
- **RFC 5737 addresses cannot be used as "public" in a test.** Python's `ipaddress` reports
  `192.0.2.0/24`, `198.51.100.0/24` and `203.0.113.0/24` as private, so a stubbed resolver that
  answers `203.0.113.7` is refused. The suite uses `93.184.216.34` and says why in a comment.
- **One existing test had to be adjusted.** `test_send_sync_classifies_push_service_status_codes`
  now stubs the resolver, because `_send_sync` judges the endpoint before it sends and would
  otherwise never reach the classifier. Its assertions are untouched; N3 is the chunk that rewrites
  those.
- **No frontend change.** The new 400 reaches `usePushSubscription.enable()` through the existing
  `catch`, which shows "Could not enable push notifications on this device." The refusal is
  unreachable for a browser talking to a real push service (all of them are public `https://`), so
  surfacing the server's wording was left for N5, which owns the push lifecycle UI. The regenerated
  `openapi.json` differs only in the endpoint's description; no response schema changed, so no
  committed frontend file moved.

### N1 notes and deviations

- **Where the shared helper lives.** `subject_line()` is in
  [`notify/transports.py`](../../CheckCheck/backend/checkcheckserver/notify/transports.py), next to
  `build_mime_message`, because that is the module that owns the header constraint being worked
  around. `render.py` already imported from it; `invitation.py` now does too, which adds no cycle
  (transports imports only `config` and `log`).
- **How it is applied.** `_subject_for_one`, `_subject_for_many` and `invitation._subject` each
  became a two-line wrapper over a `_wording…` function that holds the old body unchanged. The
  wrapper, rather than a call at the one place in `render_email`, so a subject built by a future
  caller is sanitised whether or not that caller remembers to.
- **The push title was left alone.** `_push_title` interpolates the same free text, but a newline in
  a JSON payload is not a delivery failure, and push is N2 to N5 territory. Worth a glance when N3
  gives `push_payload` its byte budget.
- **Deviation worth knowing about, finding 7.** `count_recent_for_user` now counts only rows with a
  `notification_id`, exactly as the finding suggested. That marker is also absent from a
  notification mail queued for a user who has the **in-app** channel switched off for that type:
  `emit_notification` writes no feed row in that case, so `_queue_email` has no notification id to
  key on and the mail no longer counts against `NOTIFY_EMAIL_MAX_PER_USER_PER_HOUR`. The cap is a
  flood backstop rather than a correctness rule and the combination is rare, so this was left as it
  is rather than growing the change; closing it properly means giving invitation and test rows a
  `user_id` of `None` and tracking the sender in the payload, which is the alternative the finding
  names.
- **Finding 11 is defence in depth and tests as such.** A minted token is base64url plus one dot, so
  `quote()` changes nothing about a real one. The test asserts that the form action is exactly
  `UNSUBSCRIBE_PATH?token={quote(token)}` and that the token survives the round trip through the
  page, which is the "the two paths agree" property; there is no way to drive a token containing a
  character that needs encoding through the confirm page, because such a token never verifies.
- **Test placement.** The finding 7 case went into `tests_public_link_email.py` (it needs the
  invitation endpoint) and the unsubscribe round trip into `tests_notification_wiring.py` (next to
  the existing end-to-end unsubscribe tests) rather than into `tests_email_templates.py`, which
  never touches HTTP.
