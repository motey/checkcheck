# Plan: system notifications (browser and installed-PWA push)

**Status:** P1 done (2026-08-03). Written 2026-08-03 with the maintainer, turning two rough
notes (auto-detect time zone; OS-level notifications for the browser and the
installed PWA) into an implementation brief. Follows
[`EMAIL_NOTIFICATIONS.md`](EMAIL_NOTIFICATIONS.md) and
[`DATE_REMINDERS.md`](DATE_REMINDERS.md) directly: this plan adds a fourth
delivery channel, `push`, to the preference matrix and outbox those built, and
reuses both without changing their shape.

This is smaller than the email plan (no new architecture, one new table, one new
transport), so it is split into two backend/frontend chunks plus one small,
unrelated polish item, rather than six.

---

  `CheckCheck/openapi.json` and the frontend types (`bun run postinstall`).
- End every session by overwriting `NEXT_SESSION.md` with a cold-start prompt

## 1. Orientation: what exists today

- **Three delivery channels** already exist: `in_app` (the bell, no outbox row),
  `email` and `webhook`. The matrix, the resolver and the outbox are all
  channel-generic:
  [`notify/prefs.py`](../../CheckCheck/backend/checkcheckserver/notify/prefs.py)
  (`PreferenceChannel`, `CHANNEL_MODES`, `resolve_mode`), the `NotificationChannel`
  enum in
  [`model/notification_outbox.py`](../../CheckCheck/backend/checkcheckserver/model/notification_outbox.py),
  and the channel dispatch in
  [`notify/outbox.py:320-340`](../../CheckCheck/backend/checkcheckserver/notify/outbox.py)
  (`_deliver_claimed`, currently `webhook` or `email`, anything else fails the
  row loudly as "not implemented"). Adding `push` means adding one more `enum`
  member and one more branch, not new architecture.
- **Four notification types** exist:
  `card_shared`, `card_invited`, `public_link_opened`, `reminder_due`
  ([`model/notification.py:30-41`](../../CheckCheck/backend/checkcheckserver/model/notification.py)).
  Every one of them is a candidate for a push notification; nothing here adds a
  fifth type.
- **`user_notification_settings`** already carries a per-user `timezone` column
  ([`model/user_notification_settings.py`](../../CheckCheck/backend/checkcheckserver/model/user_notification_settings.py)),
  used today for mail timestamps and reminder recurrence. The frontend already
  has `detectTimezone()` in
  [`utils/notificationSettings.ts:276`](../../CheckCheck/frontend/utils/notificationSettings.ts),
  but it is only used to pre-highlight the picker; nothing saves it
  automatically.
- **The PWA service worker** is `@vite-pwa/nuxt` in **`generateSW`** mode
  ([`nuxt.config.ts:100-154`](../../CheckCheck/frontend/nuxt.config.ts)):
  Workbox generates the whole `sw.js`, precaching the app shell and never
  touching `/api/*`. There is no hand-written service-worker file today. Adding
  a `push` event listener does **not** require switching to `injectManifest`
  (which would mean hand-maintaining the precache manifest): Workbox's
  `generateSW` accepts `importScripts`, a list of extra script URLs the
  generated worker loads with `self.importScripts(...)` at the top. A small,
  separately-authored `public/sw-push.js` with the `push` and
  `notificationclick` handlers, referenced that way, is the reasonable-effort
  path and the one this plan uses.
- **The outbox's payload-snapshot and retry-classification pattern**
  (`TransientEmailError`/`PermanentEmailError` in `transports.py`,
  `TransientWebhookError`/`PermanentWebhookError` in
  [`notify/webhooks.py`](../../CheckCheck/backend/checkcheckserver/notify/webhooks.py))
  is exactly what a push transport needs too: a push service can be briefly
  down (retry) or can report the subscription is gone (permanent, but scoped to
  *that one subscription*, see section 4).

## 2. Decisions settled with the maintainer (2026-08-03)

1. **Payload encryption and VAPID signing use `pywebpush`.** It wraps RFC 8291
   payload encryption and VAPID JWT signing, and is the de facto standard
   library for this (pulls in `py-vapid`, `http_ece`, `cryptography`, most
   already transitive dependencies here). It is synchronous (built on
   `requests`), so the transport runs each call through `asyncio.to_thread`,
   same reasoning as any blocking library called from async code. Rejected:
   hand-rolling RFC 8291/8292 with `cryptography` alone. It would avoid one
   dependency and a thread hop, but this is exactly the kind of narrow,
   easy-to-get-subtly-wrong cryptography where a smaller blast radius of
   reviewers is a real cost, not a saving.
2. **VAPID keys are explicit operator configuration**, `VAPID_PUBLIC_KEY` /
   `VAPID_PRIVATE_KEY` (`SecretStr`) / `VAPID_CONTACT_EMAIL` in `config.py`,
   boot-validated when `NOTIFY_PUSH_ENABLED` is true, exactly the
   `EMAIL_SMTP_HOST` pattern. A `gen_vapid_keys.sh` helper (parallel to the
   existing config/test scripts) generates the pair once for an operator to
   paste in. Rejected: generating a key pair automatically on first boot and
   persisting it in the database. That would be more convenient, but this
   codebase has no notion of server-wide (not per-user) database-backed
   settings today, and inventing that mechanism only for this would be new
   architecture in a plan that otherwise adds none.
3. **Push notifications default to minimal content, independent of
   `NOTIFY_EMAIL_CONTENT_MODE`.** A push notification sits on a lock screen,
   which can be visible to anyone near the device, a more exposed surface than
   an email inside an inbox app behind its own unlock. A new
   `NOTIFY_PUSH_CONTENT_MODE` (`full` / `minimal`, default `minimal`) lets an
   operator who wants full detail on push opt in explicitly; it does not
   inherit the email instance's choice.
4. **The stored time zone re-syncs to the browser's own on every login**, not
   only when it was never set. This is a genuine behavioral trade-off, not a
   free improvement: a user who deliberately keeps a fixed zone (for example,
   wanting reminders to stay on home-city time while traveling) has no way to
   pin it once this ships, since every login silently overwrites the stored
   value with `detectTimezone()`. The settings modal must say so in one line
   next to the picker ("kept in sync with this device") so it is a documented
   behaviour, not a surprise a user discovers by having a reminder fire at the
   wrong local hour after a trip.

**A fact, not a decision, that shapes the frontend work and needs to be said
plainly:** Web Push does **not work in mobile Safari at all** unless the site
has been added to the home screen (iOS 16.4+, standalone display mode only).
This is an Apple platform restriction with no code-side workaround. A user on
an iPhone who has CheckCheck open in a normal Safari tab will never be able to
subscribe, whatever this plan builds. See section 7 for how the UI should
handle that (detect the situation, explain it, do not offer a button that
silently fails).

## 3. Data model

### 3.1 `push_subscription` (new table)

One row per browser/device subscription. Unlike `webhook_url` (one per user),
a user can have several devices, so this is its own table with `user_id` as a
plain foreign key, not the primary key.

```python
class PushSubscription(TimestampedModel, table=True):
    __tablename__ = "push_subscription"
    id: uuid.UUID                       # primary key
    user_id: uuid.UUID                  # FK user, CASCADE
    endpoint: str                       # the push service URL, unique (see below)
    p256dh: str                         # subscription public key, base64url
    auth: str                           # subscription auth secret, base64url
    user_agent: Optional[str]           # snapshot at subscribe time, for the device list UI
    last_seen_at: datetime              # bumped on every successful delivery
```

`endpoint` is globally unique (it already encodes the push service and a
per-subscription token): a `UNIQUE` constraint is what makes re-subscribing the
same browser idempotent (upsert on conflict) rather than accumulating
duplicate rows that all try to push to the same now-defunct or same-again
endpoint.

### 3.2 Channel additions (no schema change to either table)

- `NotificationChannel` in `model/notification_outbox.py` gains `push`.
- `PreferenceChannel` in `notify/prefs.py` gains `push`. `CHANNEL_MODES[push] =
  (off, immediate)`, the same as `webhook`: a push notification is a live
  event, not something to batch into a digest.
- `CODE_DEFAULT_MODES[push] = off`, following the existing rule that a channel
  nobody has configured starts silent. `NOTIFY_DEFAULT_MODES` can turn it on
  per type at the operator's deliberate choice, same as every other channel.
  In practice this is close to moot either way: a row is only ever enqueued for
  a user who has at least one `push_subscription`, so "on by default" mostly
  affects a user who has already subscribed on a device, which is itself an
  opt-in act.
- The outbox payload for a `push` row snapshots `{title, body, url, tag}`:
  `title`/`body` already redacted per `NOTIFY_PUSH_CONTENT_MODE` at enqueue
  time (same reasoning as the email/webhook renderer redacting before the row
  exists, never inside the transport); `url` is the deep link
  `/?card={cl_id}&n={notification_id}` built from `SERVER_PUBLIC_URL`, reusing
  the exact link shape `notify/render.py` already builds for email; `tag` is
  the same `dedupe_key` the outbox uses for coalescing, so the OS collapses
  repeated notifications about the same thing (five shares from one actor show
  one system notification, updated, not five stacking up).

## 4. The push transport

New `notify/push.py`, mirroring `notify/webhooks.py`'s shape:

- `TransientPushError` / `PermanentPushError`, consumed by the outbox's
  existing retry policy exactly like the email and webhook errors are.
- **Fan-out happens inside the transport, not at enqueue time.** One outbox row
  is `(user_id, notification_id, channel=push)`, same as every other channel,
  but delivering it means looping over every `push_subscription` row for that
  user and calling `pywebpush(...)` (via `asyncio.to_thread`) once per
  subscription. This is the one real structural difference from email/webhook,
  where the target is fixed at enqueue time.
- **Per-subscription outcome, not per-row.** `pywebpush` raising a 404 or 410
  means that *specific* subscription is gone (the browser un-registered it, the
  user cleared site data, and so on): delete that `push_subscription` row and
  keep going, it never causes the outbox row itself to fail or retry. A 429 or
  5xx from the push service is transient and should retry the outbox row as a
  whole (mirroring the existing retry/backoff policy). The row's own status
  is `sent` if at least one subscription actually received it, `failed` only
  once **every** subscription attempt came back permanent, and cancelled with
  no error if the user had zero subscriptions at delivery time (see below).
- **"No subscription, no send", mirroring email's "no address, no send"
  (section 4.1.4 of the email plan).** If a user has zero `push_subscription`
  rows at **enqueue** time, `emit_notification`'s fan-out does not create a
  push outbox row at all, exactly like it already skips email for a user with
  no address. A subscription added *after* enqueue but before the row comes
  due is still picked up normally, since delivery re-reads the subscription
  table at send time rather than snapshotting device targets.
- `NOTIFY_PUSH_TTL_SECONDS` maps to the Web Push `TTL` header (how long the
  push service should hold an undeliverable message for an offline device),
  and `VAPID_CONTACT_EMAIL` becomes the VAPID JWT's `sub` claim
  (`mailto:...`), which most push services require to reach out to an operator
  about abuse.

## 5. Configuration

| Setting | Default | Purpose |
|---|---|---|
| `NOTIFY_PUSH_ENABLED` | `false` | Master switch. Off means no push subscription is ever created or delivered to, and the settings UI hides the push column. |
| `VAPID_PUBLIC_KEY` | `None` | Required when `NOTIFY_PUSH_ENABLED`. Validate at startup, and also served (public, not secret) to the client via `/api/public-config`. |
| `VAPID_PRIVATE_KEY` | `None` (`SecretStr`) | Required when `NOTIFY_PUSH_ENABLED`. Never leaves the server. |
| `VAPID_CONTACT_EMAIL` | `None` | Required when `NOTIFY_PUSH_ENABLED`. Becomes the VAPID JWT `sub` claim. |
| `NOTIFY_PUSH_CONTENT_MODE` | `minimal` | `full` / `minimal`, independent of `NOTIFY_EMAIL_CONTENT_MODE`. See decision 3. |
| `NOTIFY_PUSH_TTL_SECONDS` | `86400` | Web Push `TTL` header: how long a push service holds a message for an offline device before giving up. |
| `NOTIFY_PUSH_MAX_PER_USER_PER_HOUR` | `20` | Same blunt anti-flood backstop as `NOTIFY_EMAIL_MAX_PER_USER_PER_HOUR`, applied at enqueue. A phone buzzing repeatedly is a worse experience than a full inbox. |

`GET /api/public-config` gains `push_enabled` and `vapid_public_key` (the
public key only), next to the existing `email_enabled` and `webhook_enabled`
in
[`routes_public_config.py:58-61`](../../CheckCheck/backend/checkcheckserver/api/routes/routes_public_config.py),
so the client can hide the whole feature or build a subscription request
without a separate authenticated round trip.

`NOTIFY_DEFAULT_MODES` gains a `push` column per type, decided at
implementation time by the same reasoning already used for `email` (see
`notify/prefs.py`'s existing table); a reasonable starting point is `immediate`
for all four types, since the channel is inert until a user actually
subscribes a device.

## 7. Frontend and service worker

- **`public/sw-push.js`**, loaded via `workbox.importScripts` in
  `nuxt.config.ts`'s `pwa.workbox` block (section 1). Two listeners:
  `push` calls `event.waitUntil(self.registration.showNotification(title,
  {body, icon, tag, data: {url}}))`; `notificationclick` closes the
  notification and either focuses an existing client showing the app or calls
  `clients.openWindow(url)`, the same `/?card=&n=` URL the email deep link
  already uses, so the existing `useNotificationDeepLink` composable
  (`composables/useNotificationDeepLink.ts`) does the actual mark-as-read work
  once the page hydrates. No new deep-link contract.
- **Subscribing is an explicit user gesture, never automatic.** Browsers
  require a user gesture before `Notification.requestPermission()` behaves
  well, and an unsolicited permission prompt on page load is exactly the
  pattern users have learned to reflexively deny. A new "Enable notifications
  on this device" action (in `NotificationSettingsModal.vue`, a fourth channel
  column next to in-app/email/webhook, following the same per-cell pattern
  `utils/notificationSettings.ts` already uses) requests permission, then
  calls `registration.pushManager.subscribe({userVisibleOnly: true,
  applicationServerKey: <vapid_public_key from /api/public-config>})`, then
  `POST`s the result to `/api/user/me/push-subscriptions`.
- **The device list matters for a multi-device user.** Under the push column,
  a short list of subscribed devices (labeled by the stored `user_agent`, "this
  device" for the current one), each removable, calling the `DELETE` endpoint.
  Without this, a user who enabled push on a phone and a laptop has no way to
  see or revoke either from the other.
- **`pushsubscriptionchange`** (a push service can rotate a subscription's
  endpoint at any time, independent of anything the user does) must
  re-subscribe and re-`POST` automatically; without this handler, a device
  silently and permanently stops receiving push after a rotation with no user
  action to blame.
- **iOS detection.** When the platform is iOS and the app is not running in
  standalone (home-screen) mode, the push column should not offer the
  "Enable" button at all; it should explain, in one line, "Add CheckCheck to
  your home screen to enable notifications on this iPhone", per the platform
  fact in section 2. Offering a button that silently does nothing (or throws)
  is worse than not offering one.
- **Testing challenge worth flagging now, not at chunk time.** Playwright can
  grant the `notifications` permission (`context.grantPermissions`), but a
  real push round trip needs an actual push service, which nothing in CI can
  reach. The E2E coverage here has to mock `navigator.serviceWorker` /
  `PushManager.subscribe` (an init script stubbing a fake subscription object)
  to test the settings-UI flow, and the true wire protocol (VAPID JWT shape,
  encrypted payload) is a **backend** test against `pywebpush`'s own
  request-building, not an end-to-end browser test. Say this plainly in the
  chunk's handoff rather than skipping the test silently.

## 9. Explicitly out of scope

- **Rich notifications** (action buttons, images beyond a small icon, grouped
  notification "stacks" beyond the single `tag`-based collapse already
  described). The Notifications API supports more than this plan uses; nothing
  here needs it yet.
- **Badging** (a numeric count on the app/home-screen icon via the Badging
  API). Cross-browser support is patchy enough (no iOS Safari support at all,
  matching the push story) that it is not worth building alongside this.
- **Reliable delivery to a fully evicted browser process or a device under
  aggressive OS battery/background restrictions.** This is inherent to how
  every web push implementation works (the browser vendor's push service, not
  this server, decides whether and when to wake the device) and is not
  something a self-hosted server can improve on.
- **iOS Safari push without home-screen installation.** Stated in section 2:
  not a scoping choice, a platform restriction with no workaround.

`notify/push.py` (`pywebpush` sender behind `asyncio.to_thread`,
`Transient`/`PermanentPushError`), `push` added to `NotificationChannel` and
`PreferenceChannel` (`notify/prefs.py`), `_queue_push` in `db/notification.py`,
a `_deliver_push` branch in `notify/outbox.py`, and
`POST`/`GET`/`DELETE /api/user/me/push-subscriptions` plus
`POST .../test-push` in `routes_notification_settings.py`. `push_enabled` /
`vapid_public_key` on `/api/public-config`, and `push_enabled` also added to
the authenticated `GET .../notification-settings` response next to
`email_enabled`/`webhook_enabled` (not explicitly asked for in section 6, but
the same shape as the two channels already there).

Two things worth being precise about before touching this code:

- **The outbox row's own `dedupe_key` stays `None` for push, on purpose.**
  Section 3.2 says the payload's `tag` "is the same dedupe_key the outbox uses
  for coalescing" — read as *computed the same way* (`schedule.
  immediate_dedupe_key`), not *stored in the same column*. Setting
  `row.dedupe_key` would make `_claim_siblings` try to coalesce several push
  rows into one delivery, which is wrong here: push has no re-render-from-
  many-contexts path the way email does, and each row already fans out to
  every subscription on its own. `tag` is computed and put straight into the
  JSON payload; the row itself never coalesces, exactly like a webhook row.
- **Mixed per-subscription outcomes on one delivery attempt**, which section 4
  described by example (one 410 + one success → sent; both 410 → failed) but
  not exhaustively. The rule implemented in `_deliver_push`: the row is `sent`
  the moment *any* subscription actually receives it, whatever happened to its
  siblings on that same attempt (a sibling that failed transiently is not
  retried again for this notification — it gets the next one normally). If
  nothing succeeded and at least one failure was transient, the whole row
  retries with the usual backoff. Only when every subscription that existed at
  the start of the attempt came back permanent (and has been deleted) does the
  row become `failed`. Zero subscriptions *at delivery time* (discovered late,
  as opposed to zero at enqueue time, which skips the row entirely) is
  `cancelled`, not `failed` — not an error, the recipient just has no device
  right now.

Tests: `tests/tests_notification_push.py`, 20 cases covering the plan's P1 list
verbatim (upsert-on-repeated-endpoint, zero-subscriptions-at-enqueue skip, the
mixed-outcome and all-permanent cases above, a transient 5xx retrying with
backoff, `NOTIFY_PUSH_CONTENT_MODE=minimal` independent of
`NOTIFY_EMAIL_CONTENT_MODE`, the hourly cap, and boot validation both missing
and malformed) plus the transport's own status-code classification
(`_send_sync`, `pywebpush.webpush` monkeypatched, no network) and the four
disabled-instance HTTP checks that run straight against the live test server
(which boots with `NOTIFY_PUSH_ENABLED` off, same reasoning
`tests_notification_webhooks.py` already documents for the webhook channel).
Green on both `run_backend_tests_with_sqlite.sh` and
`run_backend_tests_with_postgres.sh` (full suite, not just the new file).

Not covered, deliberately: an end-to-end round trip through real `pywebpush`
against a live push service — nothing in CI can reach one, and the plan's own
P2 handoff note already flags this as backend-only, wire-protocol coverage
(done above) rather than a browser-level test.

One thing worth being precise about:

- **`pushsubscriptionchange` re-subscribes and re-POSTs entirely inside the
  service worker**, not the app. A push service can rotate a subscription's
  endpoint on its own at any time, including while no tab is open, so there is
  no app-side JS running to catch it. `fetch` from a service worker on the same
  origin carries the session cookie by default (no extra credentials handling
  needed), which is what makes this workable without a second auth path.
