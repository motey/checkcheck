# Issue #6: indexed nested env vars for list settings

Branch `fix/issue-6-indexed-env-lists`.

## Problem

`env_nested_delimiter="__"` turns `AUTH_OIDC_PROVIDERS__0__CLIENT_SECRET` into
`{"AUTH_OIDC_PROVIDERS": {"0": {"client_secret": ...}}}`. Nothing turns the
index keys into a list, so `List[OpenIDConnectProvider]` rejects it. The same
holds for every list setting (`NEW_USER_DEFAULT_LABELS__0=...`).

## Design

New module `checkcheckserver/config_sources.py` with one composite settings
source, `LayeredSettingsSource`, that replaces the env, dotenv and YAML
entries in `Config.settings_customise_sources` (init kwargs stay on top,
untouched).

* It calls the stock sources itself (YAML lowest, then `.env`, then the
  environment) and merges their output with a type-aware merge that walks the
  `Config` annotations.
* Env-derived output is prepared first: index keys are validated (plain
  non-negative integers only), nested strings at list/dict/object positions are
  JSON-decoded (pydantic-settings only does that where it knows the type, which
  it does not inside list items), `null` becomes None, object keys are matched
  to field names case-insensitively.
* Merge rules:
  * A complete list (YAML list, JSON env value) replaces the lower list.
  * An index dict patches the lower list entry by entry: object entries merge
    field by field, scalar entries are replaced, index == current length
    appends. A gap is an error naming the missing index.
  * Within one source, a JSON list plus indexed vars of the same setting:
    the indexed vars patch that JSON list (pydantic-settings silently dropped
    them before).
  * `NAME=null` plus `NAME__0__...` in the same source is an error.
  * Objects and dicts deep-merge as before (same as pydantic's deep_update).
* `yaml_file` moved out of `model_config` into an explicit
  `YamlConfigSettingsSource(..., yaml_file=config_file_path)`, otherwise
  pydantic-settings warns that no YAML source is configured (the composite
  hides it). Side effect: the path is read at call time, which tests use.

## Decisions taken by default

* Field-by-field merge of an indexed entry with the YAML entry at the same
  index (the issue's secret-injection use case).
* Index keys must be digits; `01` and `1` in the same layer are a duplicate
  error. Negative or named indexes are an error.
* Gaps are an error rather than silently compacting the list.
* A field default is not a layer: `NEW_USER_DEFAULT_LABELS__0=Home` alone
  gives `["Home"]`, not the patched default list. Same rule pydantic-settings
  already applies to dict settings, and it keeps a default list shortenable.
* `CONFIG_REFERENCE.md` (generated by psyplus) keeps its `NAME[*]__FIELD`
  notation; docs/configuration.md explains that `[*]` is the entry number.
  Changing the generator output was left alone.
* production-stack.md now injects the Keycloak client secret through
  `AUTH_OIDC_PROVIDERS__0__CLIENT_SECRET: ${OIDC_CLIENT_SECRET}` from `.env`.

## Empty client secret (follow-up decided by Tim)

An enabled provider with an empty (or whitespace-only) `CLIENT_SECRET` is
refused at startup by `Config._validate_oidc_client_secrets`; the message
names the entry index, display name and env var, never the value. Checked
first: there is no public-client / PKCE-only mode, `api/auth/utils.py` always
registers a confidential client and sends the secret on token exchange,
refresh and revocation. Disabled providers are not checked.

## Follow-ups

* `AUTH_OIDC_TOKEN_STORAGE_SECRET` keeps a built-in default that nothing
  enforces replacing, and docs/production-stack.md never sets it (out of scope
  here).
* `CONFIG_REFERENCE.md` `[*]` notation: left unchanged, Tim considers fixing
  it upstream in psyplus.
* psyplus (pydantic-settings-yaml-plus) `load()` likely has the same
  indexed-list bug and documents `[*]__` env names. Porting
  `LayeredSettingsSource` there and printing `__0__` is a possible later
  upstream task; the fix stays in CheckCheck for now.
